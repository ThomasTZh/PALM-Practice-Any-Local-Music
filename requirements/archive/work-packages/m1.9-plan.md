## 2. `GET /assets/{id}/metadata`

Response (JSON, 200):

```
asset_id, role, content_hash, byte_count
sample_rate, frame_count, channel_count      (null when asset.audio absent)
waveform: null | {
    cache_version, source_hash, sample_rate, frame_count, channel_count,
    levels: [{bucket_frame_count, bucket_count, tile_count, final_tile_buckets}],
    available_tiles: {level_index: [[first, last], ...]},
    final: bool
}
```

- Asset missing → 404 `ASSET_NOT_FOUND`.
- `waveform` comes from the **on-disk manifest** when present (it is the
  source of truth for progressive availability, M1.8); falls back to the
  DB row (`WaveformCacheRepository.get_for_asset`, final geometry,
  `final: true`, no `available_tiles`); `null` when neither exists.
- Manifest parse/validation failure → treat as absent (404-safe: the
  client will see the job and retry), never a 500.

## 3. `GET /assets/{id}/pcm` (contract §11.4)

Query: `start_frame: int ≥ 0`, `frame_count: int ≥ 1` (FastAPI rejects
negative/non-integer → 422).

Resolution and rules:
1. Asset must exist (404 `ASSET_NOT_FOUND`) and its file must be on disk.
2. Role must be `source_pcm` or `derived_pcm`; otherwise 422
   `NOT_PCM_ASSET` (source originals are encoded containers, not PCM).
3. Resolve the asset **once** (row + audio metadata + content hash); the
   bytes and every metadata header come from that single resolution
   (rule 7: no cross-representation mixing).
4. `start_frame > frame_count` → 422 `PCM_RANGE_OUT_OF_BOUNDS`.
5. `start_frame == frame_count` → 200, zero frames, EOF true (rule 5).
6. Frame cap per response: `min(requested, 8 MiB // (4 · channels),
   frame_count - start)` (rules 2 + 4; complete frames only, rule 3).
7. Stream in 1 MiB chunks; `Content-Length` set.

Headers (metadata side-channel; body is raw f32le interleaved):
`X-Asset-Id`, `X-Content-Hash` (representation version/hash),
`X-Sample-Rate`, `X-Channel-Count`, `X-Start-Frame`, `X-Frame-Count`
(actual), `X-EOF` (`true`/`false`).

## 4. `GET /assets/{id}/peaks/manifest`

- Asset must exist (404). The manifest is read from
  `cache/waveforms/<asset.content_hash>/manifest.json` via
  `resolve_asset_path` (cache prefix).
- Missing/invalid → 404 `NO_WAVEFORM_CACHE`.
- 200: the manifest JSON verbatim (`cache_version`, `source_hash`,
  rates, `levels`, `available_tiles`, `final`). Progressive by design:
  while a WAVEFORM job runs, `final` is false and `available_tiles`
  grows.

## 5. `GET /assets/{id}/peaks?level=&tile=`

Query: `level: int ≥ 0`, `tile: int ≥ 0`.
- No manifest → 404 `NO_WAVEFORM_CACHE`.
- `level ≥ len(levels)` or `tile ≥ levels[level].tile_count` → 422
  `PEAK_RANGE_OUT_OF_BOUNDS` (geometry is final even while building).
- Tile not in `available_tiles[level]` ranges, or file missing → 404
  `TILE_NOT_READY` (progressive: client retries; the manifest is only
  rewritten after the tile file is on disk, so a listed tile exists).
- 200: raw tile bytes, `Content-Length`, headers `X-Level`, `X-Tile`,
  `X-Bucket-Frames` (level geometry), `X-Tile-Buckets` (4096, or
  `final_tile_buckets` for the last tile).

## 6. `POST /projects/{id}/playback-preparations`

Request: `{"target_sample_rate": int 8000..192000}` (same range as
`playback_rate` jobs).

Resolution (mirrors `GET /playback`, spec §9.5, but creates work):
1. Project missing → 404; not ready → 409 `PROJECT_NOT_READY`.
2. Source asset = monitoring asset when present, else canonical.
3. Source rate == target → 200 `status: "ready"` with the source asset
   (no representation, no job).
4. Existing `PLAYBACK_RATE` representation for (source, target) whose
   asset exists → 200 `ready` with `representation_id` + asset.
5. Existing live job (`queued`/`running`/`cancelling`) of type
   `PLAYBACK_RATE` with the same `target_sample_rate` parameter → 200
   `preparing` with that `job_id` (shared preparation; spec §6.5.6 —
   never duplicate for a second tab).
6. Otherwise create a job through `JobManager.create_job` (so it is
   scheduled, not just a DB row) with the project's most recent
   completed import; → 200 `preparing` with the new `job_id`.

Response (a representation is identified by its asset in this system —
the `representations` table is keyed by `asset_id`, there is no separate
representation id):

```
status: "ready" | "preparing"
target_sample_rate: int
asset_id: uuid | null
sample_rate: int | null
frame_count: int | null
channel_count: int | null
job_id: uuid | null
```

## 9. Tests

`tests/unit/test_asset_routes.py` (new; TestClient through the real app,
same fixture pattern as `test_playback_routes.py`):
- metadata: ready canonical (waveform null); with on-disk cache
  (progressive `available_tiles`); DB-row fallback; 404 unknown asset.
- pcm: exact bytes + headers; 8 MiB cap (channel-scaled); clip at EOF;
  zero frames + EOF at the end; start beyond end → 422; negative → 422;
  `source_original` → 422 `NOT_PCM_ASSET`; 404 unknown asset.
- peaks/manifest: 404 without cache; 200 with levels + `final`;
  progressive manifest reflects `available_tiles`.
- peaks: valid tile bytes + headers; last tile uses `final_tile_buckets`;
  level out of range → 422; tile not ready → 404.
- playback-preparations (in `tests/unit/test_asset_routes.py`, with the
  other M1.9 route tests):
  same-rate → ready (source asset); existing representation → ready with
  the representation asset; live job → preparing reuses the job id (no
  duplicate); no job → preparing creates one (job visible in the
  project's job list); not-ready project → 409.
