# M2.14 plan — Portable project format (definition)

**Status (2026-10-17):** Phase 1 done (plan + ledger). Phases 2–5
pending: format module, dependency closure, project-only database
builder, tests + gates + commit. M2.13 is committed at `ff350c8`
(+ ledger `4cdf9fc`). See `docs/implementation-status.md` for the
full resume state.

Spec: `projectPlans/milestone2.md` §16. M2.14 defines the portable
project format: the ZIP64 container layout, the versioned manifest
schema, the compression policy, the dependency closure (exactly which
rows and files belong to one project), and the project-only database
extraction algorithm. **The archive writer is M2.15 (§17); the archive
reader/validator is M2.16 (§18).** No API routes, no frontend, no
user-facing save/open behavior in this work package.

Acceptance for the definition: everything M2.15 needs to write the
archive and M2.16 needs to validate it is pinned down here — member
names, manifest fields, essential/optional classification, the row
selection per table, and the isolation guarantee (the archive contains
everything needed for the selected project and nothing from unrelated
projects, §16).

## Scope guardrails

- **Definition only.** No ZIP writing (M2.15), no archive reading
  (M2.16), no routes, no frontend. The modules in this package are
  import-safe and dependency-free (stdlib + pydantic + the existing
  domain/storage layers).
- **Streaming contract.** The format is defined so the writer never
  loads the complete archive into memory: members are addressed by
  path and size, and the manifest lists per-member uncompressed size
  and SHA-256 (§16.1, §16.4). The database builder snapshots via the
  SQLite backup API (WAL-safe) and copies rows in streaming
  `INSERT ... SELECT` statements.
- **Project-only database** (§16.5): the portable DB never contains
  rows of unrelated projects. Internal IDs are preserved so restored
  references stay valid.
- **Monitoring-only:** the closure and the database builder are pure
  readers of the source store; they write only the destination
  database file they are given.
- One commit per work package + ledger-hash follow-up, as before.

## Design

### Package layout

```text
src/basseparate/portable/
├── __init__.py      # exports
├── format.py        # constants, member naming, compression policy, manifest schema
├── closure.py       # dependency closure → PortablePlan
└── database.py      # project-only database builder
```

### Container layout and member naming (§16.1)

Constants in `format.py`:

| Constant | Value |
|---|---|
| `FORMAT_ID` | `"basseparate.project"` |
| `CONTAINER_VERSION` | `1` |
| `MANIFEST_MEMBER` | `"manifest.json"` |
| `DATABASE_MEMBER` | `"project.sqlite"` |
| `PROVENANCE_RUNS_MEMBER` | `"provenance/separation-runs.json"` |
| `PROVENANCE_MODELS_MEMBER` | `"provenance/model-manifests.json"` |
| `ASSETS_PREFIX` | `"assets/sha256/"` |
| `WAVEFORM_CACHE_PREFIX` | `"caches/waveforms/"` |

Member naming:

- **Assets:** `assets/sha256/<content_hash><suffix>`. Suffix:
  `.pcm` for the PCM roles (`source_pcm`, `derived_pcm`, `stem`);
  for `source_original` the original upload's file extension
  (from the project's `imports.filename`, e.g. `.wav`), falling back
  to `.bin` when no import record carries a name. Other roles
  (`analysis_artifact`, `waveform_cache`) fall back to `.bin`.
- **Waveform caches:** the cache directory tree under
  `caches/waveforms/<source_hash>/` (the `manifest.json` plus the
  `level_<L>/tile_<N>.bin` pyramid files, layout per
  `domain/waveform.py`). The cache `source_hash` is the member
  directory name.
- **Database / manifest / provenance:** the fixed member names above.

### Compression policy (§16.1)

`compression_for(member: str) -> int` (zipfile constants):

- `ZIP_STORED` (0): `assets/...` (media/PCM), `caches/...` (binary
  tiles), `project.sqlite`.
- `ZIP_DEFLATED` (8): `manifest.json`, `provenance/*.json` (compact
  text).

ZIP64 is used for the container (Python's `zipfile` supports it); the
manifest records per-member uncompressed sizes so large members never
need to be buffered (§16.1).

### Manifest schema (§16.4)

Pydantic models (frozen) in `format.py`:

```python
class ManifestMember(BaseModel):
    name: str                        # archive member path
    uncompressed_size_bytes: int     # >= 0
    sha256: Sha256Hash
    essential: bool                  # False ⇒ optional/reproducible
    compression: Literal["stored", "deflate"]
    category: Literal["manifest", "database", "media", "cache", "provenance"]

class ManifestAsset(BaseModel):
    asset_id: Uuid
    content_hash: Sha256Hash
    role: str
    member: str                      # archive member path
    essential: bool

class ManifestProvenance(BaseModel):
    separation_runs: list[dict[str, Any]]   # full run records
    model_manifests: list[dict[str, Any]]   # registry metadata (no weights)

class PortableManifest(BaseModel):
    format_id: str = FORMAT_ID
    container_version: int = CONTAINER_VERSION
    project_schema_version: int
    application_version: str
    project_id: Uuid
    saved_revision: int              # projects.revision at save time
    saved_at: UtcTimestamp
    assets: list[ManifestAsset]
    members: list[ManifestMember]
    provenance: ManifestProvenance
```

This covers every §16.4 field: format identifier, container version,
project schema version, application version, project ID, saved
revision, save timestamp, asset list, per-member uncompressed size,
per-member hash, essential/optional classification, and model/run
provenance references.

**Essential/optional classification** (`is_essential_asset`):

- Essential: `source_original`, `source_pcm`, `stem`, and
  `derived_pcm` assets that are not pure playback-rate caches
  (i.e. the monitoring downmix). `source_original` and the canonical
  PCM are essential to the project; the downmix is included "when
  applicable" (§16.2).
- Optional (reproducible): `derived_pcm` assets whose only
  representation is `playback_rate` (device-sample-rate caches,
  §16.2), `waveform_cache` assets, and the waveform cache members.

### Dependency closure (§16.2, §16.3)

`compute_portable_plan(conn: sqlite3.Connection, project_id: str) ->
PortablePlan` in `closure.py`, one read transaction:

1. Load the `projects` row (missing ⇒ `PortableFormatError`).
2. Seed asset ids: the project's `source_asset_id`,
   `canonical_asset_id`, `monitoring_asset_id` (non-null), plus every
   `project_assets.asset_id` of the project.
3. Load the project's `separation_result_sets`; parse each
   `record_json` (`SeparationResultSet`) and add `source.asset_id`,
   `reference_mix.asset_id`, `bass_residual_asset_id` (when present).
4. Load the `stems` of those result sets; parse each `record_json`
   (`StemRecord`) and add `audio_asset_id`.
5. Fixpoint over `representations`: for every asset in the closure,
   add its non-null `parent_asset_id`. (Keeps representation FKs
   resolvable in the portable DB.)
6. Load `assets` for the closure; a missing asset is a dangling
   reference ⇒ `PortableFormatError`.
7. `waveform_caches` for the closure assets (member prefix
   `caches/waveforms/<source_hash>/`).
8. Provenance: the project's `separation_runs` records (full
   `record_json`), and the checked-in model registry entries
   (serialized `ModelManifest` metadata — names, hashes, sizes,
   licenses; **never weights**, §16.3).

`PortablePlan` (frozen dataclass) carries: the project row, the
`PortableAsset` list (id, content_hash, role, relative_path,
media_type, byte_count, archive `member`, `essential`), the
`PortableWaveformCache` list (cache_id, asset_id, source_hash, member
prefix), the provenance run records, the registry model manifests, and
the derived id sets (`asset_ids`, `result_set_ids`, `run_ids`) the
database builder selects on.

**Excluded by construction** (§16.3): model weights and the Python
environment (registry metadata only), unrelated projects (the closure
is rooted at one project), unreferenced global cache entries (only
caches of closure assets), partial job outputs (only published,
referenced assets), logs/auth/browser data (never project state).
Export artifacts (M2.13 `data/exports/*.wav` and `export_artifacts`
rows) are **excluded**: they are reproducible deliverables of a
documented job, not in the §16.2 inclusion list, and are hash-deduped
across projects. The export `media_jobs` rows remain as project
history.

### Project-only database builder (§16.5)

`build_portable_database(source_db: Path, project_id: str,
destination: Path) -> None` in `database.py`:

1. **Consistent snapshot:** open the source read-only and use the
   SQLite `backup` API to produce a snapshot file. This is
   WAL-safe (the backup API handles WAL state) and never copies the
   live file bytes.
2. **Schema reproduction:** attach the snapshot to a fresh database;
   replay only the DDL from `snapshot.iterdump()` (`CREATE TABLE`,
   `CREATE INDEX`, `PRAGMA user_version`) so the portable DB has the
   exact current schema with no data.
3. **Row copy (streaming, IDs preserved):** `INSERT INTO <table>
   SELECT ... FROM snapshot.<table> WHERE ...` per table, using the
   closure predicates:
   - `projects`: the target row only.
   - `assets`: `id IN asset_ids`.
   - `project_assets`: `project_id = target`.
   - `imports`: `project_id = target`.
   - `representations`: `asset_id IN asset_ids` (parents are in the
     closure by step 5 of the closure).
   - `waveform_caches`: `asset_id IN asset_ids`.
   - `markers`, `project_history`: `project_id = target`.
   - `separation_runs`: `project_id = target`.
   - `separation_result_sets`: `project_id = target`.
   - `stems`: `result_set_id IN result_set_ids`.
   - `media_jobs`: `project_id = target`.
   - `export_artifacts`: **not copied** (excluded, above).
4. **Integrity:** `PRAGMA foreign_key_check` must return no rows.
5. **Isolation proof:** `projects` has exactly one row (the target);
   every `project_id` column in the portable DB equals the target.
   Any violation ⇒ `PortableFormatError` and the destination is not
   left behind (built in a temp file, moved into place at the end).
6. The destination is a standalone database: default (delete) journal
   mode, clean close, no `-wal`/`-shm` sidecar dependency — the
   archived `project.sqlite` is self-contained.

### Provenance payloads

- `provenance/separation-runs.json`:
  `{"version": 1, "runs": [ <full SeparationRun record dicts> ]}`.
- `provenance/model-manifests.json`:
  `{"version": 1, "models": [ <serialized registry ModelManifest
  dicts> ]}` (metadata only; the runs reference it by
  `model_manifest_hash`).

Both are small text members (deflate). The serialization helpers live
in `closure.py` (`separation_runs_payload`, `model_manifests_payload`)
so M2.15 writes exactly what M2.16 will validate.
