# M2.9 plan — Integrate the time-stretch engine correctly

**Status (2026-10-16):** Phase 1 (this plan + ledger) done. Phases
2–9 pending. All M2.8 work is committed (`79d898e`); the tree is
clean. See `docs/implementation-status.md` for the full resume state.

Spec: `projectPlans/milestone2.md` §11. M2.8 delivered the aligned
track stack, the monitoring-only stem mixer, and the N-source
shared-timeline transport at 1×. This work package adds **pitch-preserving
playback speed** (0.25×–2.0×) by integrating Signalsmith's C++
stretch core through a small project-owned WASM wrapper inside the
existing AudioWorklet.

## Scope guardrails

- The stretch engine is **monitoring-only**: it never writes source
  or annotations (§11.7.7). Speed is a per-project practice setting
  (`practice_state.playback_speed`, already in the domain at
  0.25…2.0).
- No 1× bypass path, no three-time-domain transport ledger, no
  priming rework — those are M2.10 (§12). M2.9 routes **all**
  playback (including 1×) through the stretcher and records its
  latencies in the engine profile.
- No loops (M2.11+), no pitch shift (stays at 0 semitones, §11.5.2),
  no formant manipulation (§11.5.3).
- The app must launch with **no compiler present**: WASM artifacts are
  built once in a pinned environment and bundled into the repo
  (§11.3.10–11).

## Design

### Environment + reproducible WASM build (Phases 2–3)

- `third_party/emsdk` (gitignored): the official emsdk workflow,
  pinned to a recorded release tag (resolved + recorded in Phase 2,
  not a moving `latest`). `third_party/signalsmith-stretch`
  (gitignored): the upstream repo at a pinned commit (recorded in
  Phase 2).
- `frontend/src/playback/stretch/` (committed):
  - `stretch_wrapper.cpp` — the project-owned wrapper. Owns one
    Signalsmith `Stretch` instance and exposes the §11.4 contract to
    JS: create/configure, report input + output latency, process
    (specified in/out frame counts), set rate, reset, flush tail,
    destroy. Processing buffers are pre-allocated at create time
    (fixed max block, e.g. 4096 frames × 2 ch); the WASM heap never
    grows from the audio callback (§11.4).
  - `build.mjs` — the explicit developer setup/build command
    (§11.3.4): runs the pinned emsdk's `emcc` with `-O3`,
    `--no-threads`, MODULARIZE, `ENVIRONMENT=worker`; emits **scalar**
    and **SIMD** (`-msimd128`) variants (§11.3.6–7).
  - `dist/` — the built artifacts (glue JS + `stretch-scalar.wasm` +
    `stretch-simd.wasm`), bundled locally (§11.3.10).
  - `BUILD.md` — build manifest: emsdk release, Signalsmith commit,
    wrapper source hash, artifact SHA-256 hashes, build date
    (§11.3.9).
  - `NOTICES-signalsmith.md` — preserved MIT notices (§11.3.2).
- Verification (§11.3.11): a test asserts the bundled artifacts
  load + process in Node with no toolchain on PATH.

### Engine profile + host API (Phase 4)

- `stretch-profile.ts`: the chosen configuration recorded per
  §11.5.1–5 — Signalsmith's default quality, 0 semitones, no formant,
  the measured **input and output latency** (from the wrapper's
  latency reports), and the measured audio-thread cost (dev
  measurement recorded in the evidence doc).
- `stretch-host.ts`: loads + instantiates the bundled WASM (fetch the
  `.wasm`, `WebAssembly.instantiate`), selects **SIMD only after
  capability detection** (`WebAssembly.SIMD` / probe module,
  §11.3.7), and exposes the processor interface:
  `create() → {latencyInFrames, latencyOutFrames, process(in, out) →
  consumedInFrames, setRate(r), reset(), flushTail() → frames,
  destroy()}`.
- Node unit tests against the **real WASM**: impulse pass-through
  timing (input + output latency), rate-consumption ratio (2× consumes
  ≈ 2× the input), reset clears state, tail flush, scalar == SIMD
  output (within tolerance).

### Worklet integration (Phase 5)

- The graph follows §11.1: per-stem gain/pan/mute/solo → stereo sum
  → **Signalsmith Stretch** → master gain → (limiter, in the
  transport graph) → output. In `MixState`, the stereo mix that
  currently becomes the output is instead fed to the stretcher; the
  stretcher's output becomes the quantum output.
- **Variable source consumption** (§11.1: "the stretch engine must
  control how many source frames are consumed"): per quantum the
  stretcher demands `inFrames` for `outFrames` of output (fractional
  source-consumption accumulator inside the wrapper, §11.7.3).
  `MixState`'s shared cursor `take` becomes the stretcher's demand
  (capped by buffered/endpoint as today). The `anchor` message keeps
  reporting the consumed **source** frame (now rate-dependent).
- **Rate transitions** (§11.7): the transport posts
  `rate {value}`; the wrapper owns the rate-transition state — the
  effective rate is smoothed over ≈ 50 ms of render time. Pitch is
  never changed.
- The `init`/`processorOptions` path gains the engine profile
  (latencies); the legacy no-stretch path is **not** preserved —
  M2.9 always stretches (the bypass is M2.10 §12.4). The 1-source
  `init` shape stays (M1 fixtures), with the stretcher inside.
- `worklet-core` tests: consumption ratio at 0.5×/2×, rate ramp
  smoothness, consumed-frame bookkeeping across a rate change, reset,
  underrun behavior with variable demand.

### Transport (Phase 6)

- **Input-rate fill**: the fetch lookahead is in *source* frames; at
  speed `s` the source is consumed at `s × sampleRate` frames/s, so
  the fill loop budgets `seconds × rate × s` (the 1 s chunk / 2 s
  prebuffer / 8 s steady shapes are kept, scaled by `s`).
- **Position mapping across transitions** (§11.7.5, minimal): the
  transport keeps a bounded segment list — `{outputStart,
  outputEnd, sourceStart, sourceEnd, rate}` — appended on rate change
  and seek; `getAudiblePosition` maps output time through the current
  segment (extrapolation frozen while paused as today). The full
  three-time-domain ledger is M2.10.
- `setRate(speed)` public API: posts `rate`, remembered for a fresh
  graph; the engine-profile latencies (input + output) are folded
  into the audible-time mapping alongside the limiter delay.

### Domain + API (Phase 7)

- `SetPlaybackSpeedOp {speed}` — undoable (not in
  `HISTORY_EXCLUDED_TYPES`), validated 0.25…2.0 (422 on violation);
  writes `practice_state.playback_speed`. No pre-validation beyond
  range (speed is independent of the result set).

### Frontend state + UI (Phase 8)

- `useProjectCommands`: `set_playback_speed` sender (immediate, never
  debounced).
- Speed control in the `PlaybackPanel` (spec §11.6): slider
  0.25…2.0 step 0.01, numeric entry, presets 0.25 / 0.5 / 0.75 / 1.0 /
  1.25 / 1.5 / 2.0, "1×" reset. Invalid numeric input is clamped and
  the current value is preserved (§11.6). **Gesture coalescing**
  (§11.7.8): slider `input` updates local display only; one op is
  sent on `change` (release) / Enter / preset / reset.
- `PlaybackPanel` forwards the committed speed to
  `transport.setRate`.
