# M2.17 — API and command additions (spec §19)

## Objective

Expose the analysis, model, and project interfaces of spec §19, and wire
separation requests from the API to the isolated analysis environment:
`POST /projects/{id}/runs` creates a durable run + job, the analysis worker
runs `analysis/separate.py`, and the publisher validates/publishes stems
(M2.6) and marks the run complete. Long work returns job IDs; the app
environment never imports PyTorch.

## Existing pieces (inventory)

| Piece | State |
|---|---|
| Device discovery, qualification store, selection (`devices.py`, `domain/device.py`) | implemented + tested (M2.2), not wired to HTTP |
| Model registry + bundle verification/provenance (`models/`) | implemented + tested (M2.3), `/models` is an empty stub |
| Separation input preparation (`media/preparation.py`) | implemented + tested (M2.4), no caller |

| Stem validation/publication (`media/publication.py`) | implemented + tested (M2.6), no caller |
| Cache key + lookup + coalescing primitives (`media/separation_cache.py`, `SeparationRepository`) | implemented + tested (M2.7) |

| Commands, undo/redo, exports, portable save/open, `/downloads/{id}` | implemented (earlier milestones) |

So M2.17 is mostly *wiring* plus the analysis worker and three new route
groups; no command additions are missing (§19.3 already shipped in
M2.1–M2.13, §19.4 transport extensions in M2.8–M2.11).

## Design decisions

### 1. Dedicated analysis worker (§4.1.7, §19.5)

- New `analysis/worker.py`, run with `analysis/.venv/bin/python`. It speaks
  the M1 protocol v2 on stdin/stdout (same envelope; `hello` version 2,
  `describe` → `capabilities`). Capabilities declare
  `separation.v1` with the parameter/result schema version (no protocol
  version bump: existing message semantics are unchanged).
- On `run` for `job_type == "separation"`, it spawns
  `analysis/separate.py` with the explicit interpreter, relays its
  JSON-lines progress (`segment` → `progress`, `fraction`), honours
  `cancel` by creating the cancel flag file, and reports `completed` with
  `{attempt_dir, record_path, stem_labels}` or `failed`.
- The script path and interpreter are flags with defaults, so tests can
  substitute a fake separator without torch.

### 2. Two worker classes in `JobManager`

- Media jobs keep the existing eager media supervisor and queue. Separation
  jobs use a second queue and a lazily started analysis supervisor, so a
  long separation never blocks playback preparation (§14.3); within each
  class the existing priorities apply (separation is the background class).
- Startup reloads queued jobs into their class; `cancel_job` routes to the
  supervisor running that job; `stop()` shuts both down. The analysis
  supervisor is stopped when idle (no long-lived torch process).

### 3. Runs: `POST /api/v1/projects/{id}/runs`

Request body: `{mode: "four_stems"|"bass_pair", device?: "auto"|"cpu"|uuid,
seed?: int}` (defaults: four_stems, auto, 0). Response:
`{run_id?, job_id?, result_set_id?, cached, coalesced}`.

Flow (project must be ready):

1. Resolve the reference plan (§6.1): stereo → canonical asset; mono →
   canonical asset; multichannel → monitoring downmix asset with the
   recorded `DownmixSpec`.
2. Resolve the model manifest (`htdemucs_ft`) and device selection
   (`/hardware` data). No qualified accelerator and no explicit `cpu` →
   409 `NO_QUALIFIED_DEVICE`; an explicitly preferred device that is
   missing/unqualified → 409 with the reason (never silently substitute).
3. Compute `transform_identity_hash` and the §9.1 cache key (engine/adapter
   constants, window/segment/shift parameters, seed, device profile,
   output geometry).
4. Coalesce: `find_active_run` → return that run (job located by
   `parameters.run_id`, `coalesced: true`).
5. Cache hit: `lookup_cached_result` (asset existence/size check) → return
   the result set (`cached: true`, no job).
6. Otherwise create the `SeparationRun` (queued, requested parameters,
   cache key, input asset + transform hash, model identity, device type and
   GPU UUID) and the `SEPARATION` job (`parameters.run_id`).

### 4. Preparation at dispatch

The manager gets an async separation-parameter builder (injected in
`app.py`), so preparation runs in the scheduler loop, not the route:

- `build_reference_plan` from the project + assets (pure).
- `prepare_separation_input` into the job staging dir (M2.4); write the
  normalization profile JSON.
- Worker parameters: prepared PCM path, profile path, output dir, device,
  seed, segment/window/overlap defaults, bundle dir, run id, model id.
- The prepared input is an intermediate: result-level caching (§9) avoids
  repeating a request; the file is removed with the job staging. The run
  records the reference/transform identity (§3.2).

### 5. Separation publisher

A `JobType.SEPARATION` publisher calls `publish_separation_result` with the
run record, staged stems, the project-rate reference mix (canonical or
downmix) for reconstruction diagnostics, project geometry, cache key, and
repositories. It queues per-stem waveform jobs. Publication is the only
transaction that exposes the result set.

### 6. Hardware interface

`GET /api/v1/hardware` → `{devices: [DeviceRecord], selection: {...}}`:
`nvidia-smi` discovery (fresh VRAM), qualification store merged
(`state/analysis/devices.json`), selection via `select_device` (no
preference in this route: first qualified GPU, else CPU offered). No
PyTorch import; `POST /runs` records the chosen device.

### 7. Models interface

- `GET /api/v1/models`: registry manifests + bundle presence (file sizes)
  + recorded verification (`state/analysis/models.json`) + qualification
  status (provenance store `state/analysis/provenance.json`).
- `POST /api/v1/models/{id}/verify`: `verify_bundle` (hash + size, no
  inference, no network) synchronously in the threadpool, records the
  result and returns the report. Unknown id → 404.

### 8. Separation results listing

`GET /api/v1/projects/{id}/separation-results` delegates to the existing
result-set listing handler (spec name; the existing `/result-sets` path is
kept for the frontend).

### 9. Schema

- `JobType.SEPARATION`; `JobStage.PREPARING_INPUT`, `JobStage.SEPARATING`.
- Migration 12 rebuilds `media_jobs` (migration 9 pattern) with the new
  CHECK values; `DATABASE_SCHEMA_VERSION` 12; test baselines.

## Invariants

- The app environment never imports torch/demucs; the analysis env is
  launched by explicit interpreter path.
- No network: model verification is local hashing; no downloads.
- Long operations return job IDs; the event loop stays responsive.
- Cancellation removes staged analysis files; failed/cancelled runs never
  become cache hits.
- Playback preparation (media class) is not blocked by separation
  (analysis class).
- Monitoring-only: job outputs are the only writes; no telemetry.
