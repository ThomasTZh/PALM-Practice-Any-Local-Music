# M2.12 plan — Extended buffering and resource limits

**Status (2026-10-17):** complete — Phases 1–7 (plan + ledger; backend
scheduler, memory bound, and runtime diagnostics; transport sizing +
worklet capacity contract; pinned loops; group readiness + fetch
priority; diagnostics UI; evidence + gates + local acceptance run).
M2.12 is committed as `M2.12: extended buffering and resource limits
(spec §14)` (+ ledger hash follow-up). M2.11 is committed at `f65370a`
(+ ledger `ce94136`). See `docs/implementation-status.md` for the full
resume state.

Spec: `projectPlans/milestone2.md` §14. M2.12 updates the Milestone 1
limits (§15.3 of `milestone1.md`: 8 s steady lookahead, 12 s retention
per representation) to speed-scaled sizing with byte and duration caps,
adds the pinned-loop byte budget (the M2.11 hook the M2.11 plan left at
`### Buffering (§13.5)`), makes group readiness explicit, separates the
thread/resource roles with a bounded media job, and collects local
runtime diagnostics. Acceptance: separation and waveform generation can
run while an already prepared song plays without routine audio
dropouts.

## Scope guardrails

- **Separation is not scheduled here.** The analysis (Demucs) runtime
  exists as a separate process (M2.2), but the separation *job type*,
  its route, and the analysis-worker dispatch are M2.17 (deferred since
  M2.5/M2.7: "no scheduler wiring (M2.17)"). M2.12 builds the
  mechanisms the M2.17 wiring needs — priority classes, a bounded media
  execution, and diagnostics — and documents the two-class policy.
  The separation half of the acceptance criterion is verified with
  M2.17; the waveform/media half is verified here.
- **No telemetry** (§14.4): diagnostics are read from `/proc`,
  `nvidia-smi`, and in-memory counters, and are surfaced only through
  the existing authenticated same-origin `/api/v1/system`.
- Monitoring-only: no source, annotation, or storage writes.
- Single commit per work package + ledger-hash follow-up, as before.

## Design

### §14.1 Source-buffer sizing

Milestone 1's single `RING_SECONDS = 12` frame cap is replaced by a
sizing policy computed once per group, in the transport (single source
of truth):

    bytesPerFrame_i = 4 * channelCount_i
    byDuration_i    = ceil(sampleRate * SOURCE_BUFFER_SECONDS)
    byBytes_i       = floor(SOURCE_BUFFER_BYTES / bytesPerFrame_i)
    capacityFrames  = min over active sources of min(byDuration_i, byBytes_i)

- `SOURCE_BUFFER_SECONDS = 24` (§14.1.3: up to 24 s per active stem
  initially) and `SOURCE_BUFFER_BYTES = 32 MiB` (§14.1.2: the byte
  cap). The duration cap binds at ordinary rates (24 s @ 48 kHz
  stereo = 9.2 MB); the byte cap binds at extreme channel counts /
  rates.
- All rings of the group get the **same** frame capacity — the stems
  are one synchronized set, and the worklet's min-across-sources budget
  stays one number (§14.2.1).
- **Speed-scaled lookahead** (§14.1.1): the M2.9/M2.10 target
  (`rate × speed × 8 s`) stays, but it is now *achievable*: capacity is
  asserted ≥ `rate × speedMax × 8 s` at 2× (16 s of source), and
  `targetAhead` is clamped to `capacityFrames − marginFrames` so the
  gate can never deadlock against a byte-capped ring.
- **Worklet contract:** the transport passes `capacityFrames` in the
  worklet `processorOptions` (and sizes the shared SABs from the same
  value). `worklet-processor.js` stops hard-coding `RING_SECONDS` for
  the transfer path and uses the provided capacity; the shared path
  keeps deriving it from the SAB length (already consistent).
- **Byte accounting:** `TransportDiagnostics` gains `bufferedBytes`,
  `budgetBytes`, `pinnedBytes`, and `stemBufferedFrames: number[]`.
  Flow-control gates keep frame semantics (frames are the DSP
  currency); the byte figures are the policy/accounting surface.
- Existing tests that pin the 12 s budget (transport flow-control
  tests) move to the new capacity; worklet tests stop asserting
  `RING_SECONDS` and inject a capacity.

### §14.1.4–5 Loop pinning (the M2.11 hook)

M2.11 streams loops with a cycling fetch cursor (no cache). M2.12 adds
the pinned-loop budget:

- **Eligibility:** at loop install, the group loop bytes
  (`len × Σ_i bytesPerFrame_i`) are compared with the remaining pinned
  budget, `PINNED_BYTES_MAX = 64 MiB` shared across the active group
  (§14.1.5). Eligible → pin; otherwise today's streaming path verbatim
  (the "fits the configured byte budget" rule of §13.5.3).
- **Fill:** ordinary loop fetches retain the frames that fall inside
  `[start, end)` (transfer mode: the returned channel arrays are
  adopted; shared mode: the payload is captured alongside the SAB
  write). A partial first pass completes the pin over subsequent
  passes; once every frame has been retained the pin is `ready`.
- **Serve:** while `ready`, pass fetches are served from the immutable
  pin — no network round trip. Shared mode copies pin frames directly
  into the SAB; transfer mode posts cloned channel views. The
  loop-head **pre-roll** (`B − PRE_ROLL_FRAMES`, the periodic tail) is
  likewise served from the pin once available, and fetched as today
  before that (§14.1.4: accounted separately from the streaming
  budget).
- **Account/release:** `pinnedBytes` sums the retained arrays across
  sources, is excluded from `bufferedBytes`/`budgetBytes`, and is
  released on loop change/disable/dispose. A new pin is admitted only
  while `pinnedBytes + needed ≤ PINNED_BYTES_MAX` (first-come across
  the group); released bytes free budget again.
- **Reuse** (§14.1.6): the pin itself is the reused immutable buffer
  (every pass, every seek); the serving path avoids per-pass
  allocation where the mode allows.

### §14.2 Group readiness

Already built (M1.13/M2.8): one shared fetch cursor, a group round
whose cursor advances by the minimum frames written, min-across-sources
`buffered` gating in the worklet, muted stems consumed/aligned, and a
synchronized start threshold. M2.12 makes the remaining rules explicit
and tested:

- **Start gate stays group-wide** (§14.2.2): playback (re)starts only
  when the *weakest* source has reached the start threshold; muted
  stems are not exempt (they stay buffered and aligned, §7.2's
  "a muted stem must either remain buffered or join only when
  synchronized data is available").
- **Group generation** (§14.2.4): the transport keeps one group
  generation, bumped once per seek/rebind; every leg of a round is
  validated against the current generation *before* any ring write or
  post, and one stale/failed leg aborts the entire round (no partial
  advancement). Covered by a multi-source stale-generation test.
- **Single-stem failure stops the group** (§14.2.5–6): a permanent
  fetch failure of any source stops all sources (transport `error`);
  a test asserts the healthy stem's position freezes and no audio
  advances. A transient starve keeps the existing coherent
  `buffering` path (underrun → resume at the start threshold).
- **Per-stem readiness is reported** (§14.2.1): the worklet's
  `buffered` message gains `stems: number[]` (per-source buffered
  frames) on top of the min value; the transport surfaces it and the
  UI shows it.

### §14.3 Thread/resource separation

Roles as built and kept:

| Role | Where |
| --- | --- |
| API process: requests, metadata, SQLite | `api/` + event loop |
| Media worker: resampling/peaks/decode | `worker/media_worker.py` subprocess |
| Analysis worker: model execution | Demucs runtime process (M2.2); **job class wired in M2.17** |
| Browser worker: range fetch + deinterleave | `playback/fetch-worker.ts` |
| AudioWorklet: mixing/stretching | `worklet-processor.js` |

New in M2.12:

- **Priority scheduling.** The job queue becomes a priority queue with
  three classes — playback preparation (`MONITORING_DOWNMIX`,
  `PLAYBACK_RATE`) > import-critical (`PROBE`,
  `CANONICAL_DECODE`) > background (`WAVEFORM`) — FIFO within a class.
  This is the "give playback preparation priority over background
  waveform work" rule; the same-class bound stays one media job at a
  time (bounded). The M2.17 analysis class gets its own runner slot;
  the queue structure admits classes without further refactoring.
- **Worker memory bound.** A new `media_worker_memory_limit_mb` config
  (default 4096) is passed to the media worker; the child applies a
  best-effort `RLIMIT_AS` before serving jobs (skipped when the
  platform lacks `resource`). It is the hard guard for runaway
  allocations; RSS is reported in diagnostics.
- **Browser fetch priority.** Playback PCM chunk fetches take
  `priority: 'high'`; waveform tile fetches take `priority: 'low'`.
  The hint is asserted in jsdom tests and is a no-op in browsers
  without support.

### §14.4 Diagnostics (local only)

A `runtime_diagnostics.py` collector in the API process gathers:

- host RAM total/free and API-process RSS/CPU (procfs);
- the media worker's RSS/CPU by PID while it runs (procfs);
- the media job state: id, type, stage, progress fraction, queue
  depth;
- GPU memory total/free from `nvidia-smi`, plus a peak-used figure
  tracked by a light background sampler (null when `nvidia-smi` is
  unavailable);
- the last separation run's elapsed seconds from the run records
  (null until M2.17 produces runs).

`GET /api/v1/system` gains an optional `runtime` object with these
fields (contract regenerated). The frontend diagnostics block
(the existing `.underrun-diagnostics` line) expands to show per-stem
buffered frames, pinned bytes/cap, underrun count, worklet callback
duration, stretcher rate/bypass, worker RSS/CPU, GPU peak, last
separation time, and the current job phase, polling `/system` every
2 s while a project is open. Worklet side, the `buffered` message
gains `stems`, `capacityFrames`, `lastCallbackMs` (the render
callback's duration measured in `process()`), and
`stretcher: {rate, bypass, warmup}`. Nothing leaves the machine.

## Phases

1. **Plan + ledger** (this file + the M2.12 ledger section).
2. **Backend: scheduler + limits + diagnostics.** Priority classes in
   `JobManager`; `enqueue_existing_job` shares the ordering;
   `media_worker_memory_limit_mb` config → worker `RLIMIT_AS`; the
   runtime diagnostics collector and the `/system` extension; tests
   (priority order, memory-limit arg, collector shape with fake
   procfs/nvidia-smi, API response).
3. **Transport sizing + worklet contract.** The capacity policy
   (`SOURCE_BUFFER_SECONDS`/`SOURCE_BUFFER_BYTES`), speed-scaled
   `targetAhead` clamp, `processorOptions.capacityFrames`, byte
   accounting in diagnostics; update the 12 s-pinned tests; new sizing
   tests (rate/channels/speed matrix, byte-cap binding, 2× headroom).
4. **Loop pinning.** `LoopPin` (eligibility, fill, serve, release),
   pre-roll from the pin, `PINNED_BYTES_MAX` accounting, diagnostics;
   tests: second pass served without fetches, pre-roll served from the
   pin, cap fallback to streaming, release on change/disable,
   identical audio across passes.
5. **Group readiness + fetch priority.** Multi-source stale-leg abort,
   single-stem failure freeze (both sources stop), muted-stem alignment
   and group start gate, per-stem `stems` reporting, `priority` hints;
   tests.
6. **Diagnostics UI.** Transport diagnostics fields through
   `PlaybackPanel`/`App`; the runtime poll and the expanded diagnostics
   block; tests for the rendering and the poll lifecycle.
7. **Evidence + gate + commit.** `docs/evidence/m2.12-buffering.md`;
   full backend gate (pytest, ruff, mypy, `check_contract.py`) and
   frontend gate (Vitest, `tsc -b` baseline, prettier); single
   `M2.12: extended buffering and resource limits (spec §14)` commit +
   `Ledger: record M2.12 commit hash (<hash>)`.

## Known deviations / notes

- Shared-mode pinning captures the fetch payload alongside the SAB
  write (one extra copy per pinned loop, bounded by the 64 MiB cap);
  transfer-mode serving clones per pass because transferables detach.
  Both are documented in the evidence.
- The priority queue changes ordering within the old single FIFO; the
  job-manager tests are updated accordingly and a new priority test
  pins the classes.
- `tsc -b` has a 32-error pre-existing baseline; no new errors.
