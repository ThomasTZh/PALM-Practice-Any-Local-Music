# M2.1 plan — Confirm prerequisites and extend the domain

Spec: `projectPlans/milestone2.md` §3 (M2.1). This is the first Milestone 2
work package. It is **domain + schema + serialization + frontend-types only** —
no Demucs runtime, no GPU, no model, no network. Later packages (M2.2+) build
the runtime on top of the records defined here.

**Acceptance (§3.6):** a result set, its audio, and its playback settings can
be represented without modifying the original source record.

## Scope in / out

In:
- New domain records: separation run, result set, stem (§3.2–3.4).
- Mixer + practice state attached to the project (§3.5).
- DB migration 6→7, version bumps, project serialization update (§3.6).
- Repository surface to persist/read the new records (round-trip).
- Regenerated OpenAPI + frontend types.
- Tests for all of the above.

Out (deferred to later M2 packages):
- Actual Demucs/PyTorch runtime (M2.2), model provisioning (M2.3), input
  preparation (M2.4), separation execution (M2.5), validation + publication
  logic (M2.6), caching (M2.7), mixer/transport/loop behavior (M2.8–M2.12),
  export (M2.13), portable project (M2.14–M2.16), API/command endpoints for
  the new records (M2.17).

### Phase 3 — Domain records (§3.2–3.4) → `domain/separation.py`
Enums:
- `SeparationMode`: `bass_pair`, `four_stems`.
- `SeparationRunStatus`: `queued, running, completed, failed, cancelled,
  interrupted` (mirrors the job state set).
- `ValidationStatus`: `pending, valid, invalid`.
- `DeviceType`: `cpu`, `cuda`.
- `StemRole`: `vocals, drums, bass, other` (the four declared source labels).

Sub-models:
- `SourceIdentity`: source_asset_id, source_hash, sample_rate,
  duration_frames.
- `ReferenceMixIdentity`: asset_id, hash, transformation_hash.

Records:
- `SeparationRun` (§3.2): run id, project id, input asset + transformation
  hash, requested mode, model manifest id + hash, engine version, adapter
  version, **requested_parameters** (dict) and **effective_parameters**
  (dict | None — separate so memory-recovery retries stay auditable), random
  seed, device type, gpu_uuid, runtime_versions (dict), start/end timestamps,
  status, result_set_id, warnings (list[str]), timing_metrics (dict).
  Invariants: gpu_uuid present only for cuda; result_set_id present only when
  completed; effective_parameters defaults to None; started_at set once past
  queued.
- `SeparationResultSet` (§3.3): id, run id, project id, source identity,
  output sample rate / channel count / frame count, available stem roles
  (list, no duplicates), stem ids (list[Uuid]), bass-residual asset id (opt),
  reference-mix identity, reconstruction_metrics (dict), validation status,
  created_at. A result set is *available* only once its required assets are
  valid: `validation_status == valid` ⇒ non-empty stems + positive frame count.
- `StemRecord` (§3.4): id, result-set id, role (from the model's declared
  label, not a tensor index), display name, audio asset id, sample rate,
  channel count + layout, frame count, alignment offset (int, normally 0,
  bounded), waveform-cache asset id (opt), playback-representation ids
  (list[Uuid]), confidence (reuse `domain.confidence.Confidence`),
  provenance (dict).

### Phase 4 — Mixer + practice state (§3.5) → `domain/practice.py`
- `PlaybackMode`: `original`, `bass_pair`, `four_stems`.
- `TrackSettings`: gain (0–2), mute, solo, balance (−1..1), visible,
  display_height (0.25–2).
- `PracticeLoop`: id, name, start_frames < end_frames, created_at, updated_at.
- `PracticeState`: playback_mode, active_result_set_id (opt), tracks
  (dict[str, TrackSettings], bounded), master_gain (0–2), monitoring_limiter
  (bool), playback_speed (0.25–2.0), loops (list), active_loop_id (opt),
  loop_enabled (bool). Invariants: active_loop_id references an existing
  loop; stem modes (bass_pair/four_stems) require active_result_set_id and
  original forbids it.
- `ProjectRecord` gains `practice_state: PracticeState = default`.

### Phase 5 — Versioning (§3.6)
