# M2.13 plan — WAV stem export

**Status (2026-10-17):** Phase 1 done (plan + ledger). Phases 2–5
pending: backend job plumbing + export storage + delivery; worker DSP;
frontend export panel; evidence + gates + commit. M2.12 is committed at
`0e88c7a` (+ ledger `1b79846`). See `docs/implementation-status.md` for
the full resume state.

Spec: `projectPlans/milestone2.md` §15. M2.13 exports the published
stems of an immutable separation result set (bass, others residual,
four-stem outputs, or any selected subset) as WAV files at the source
or an alternate sample rate, in 16-bit, 24-bit (default), or float32,
with optional linked peak normalization to −1 dBFS, triangular dither
when reducing to integer PCM, and FFmpeg encoding with RF64 fallback.
Acceptance: exported stems line up when imported into a DAW and match
the intended raw or explicitly normalized samples (§15, §20.8).

## Scope guardrails

- **Full source duration at original speed only** (§15.1). Selection,
  mixer-rendered, loop-queue, and stretched exports are later additions.
- **Raw exports ignore monitoring state** (§15.4): mixer mute/solo/pan/
  gain, master volume, the monitoring limiter, and playback speed never
  reach an export job. The worker reads published stem assets directly.
- **Separation scheduling stays with M2.17.** Export is a media-worker
  job (spec §14.3: "media worker: resampling/peaks/export"), one at a
  time like every other media job.
- **Managed storage only** (§15.3.5): the app resolves staging and
  `data/exports/` destinations; the browser's final filesystem path is
  the user's own download choice and is never project state.
- Monitoring-only for the project: no source, annotation, or project
  state writes. Exports add managed files and artifact records only.
- One commit per work package + ledger-hash follow-up, as before.

## Design

### Export request and job shape (§15.1, §15.3.1–3, §19.2)

- New `JobType.EXPORT`. Route `POST /api/v1/projects/{project_id}/exports`
  (the §19.2-reserved project interface), honoring `Idempotency-Key`
  through the existing `IdempotencyStore` (the command-route pattern).
- Request (`CreateExportRequest`):
  - `result_set_id: UUID | null` — default: the project's active
    result set (practice state), else its valid set; must belong to
    the project and be an immutable published set.
  - `asset_ids: UUID[] | null` — the selected stem assets; default:
    every stem of the set. Each id must be a stem `audio_asset_id` of
    that set (§15.1 "all stems in a selected group").
  - `format: 'wav16' | 'wav24' | 'wav32f' = 'wav24'` (§15.2).
  - `sample_rate: int | null` — `null` = source rate (default); else
    `44100` or `48000` (§15.2).
  - `normalize: 'off' | 'linked_peak' = 'off'` (§15.2; one linked gain
    across the selected stems, never per-stem).
- Response: the created `MediaJob` (201). Progress and outcomes ride the
  existing job routes; the terminal `result` carries the artifact list.
- Validation resolves the set via
  `SeparationRepository.get_result_set_detail` (one-connection set + run
  + stems read), checks the stem assets on disk (`frames × channels × 4`
  size), and rejects impossible requests before job creation where the
  data allows (`EXPORT_RESULT_SET`, `EXPORT_STEM_MISSING`).

### Asset-sourced jobs (pre-existing gap, fixed here)

M2.7's `queue_stem_waveforms` creates `WAVEFORM` jobs with
`parameters={"asset_id": …}` and no import. The manager's `_run_job`
requires an import-backed source file for *every* job, so those jobs
currently fail `NO_SOURCE` at execution (latent pre-existing defect;
M2.7 tested creation, not execution). Export jobs hit the same
constraint. Fix: `_run_job` computes parameters first for import-less
jobs and resolves the run source from them (waveform:
`parameters["source_path"]`; export: the first stem's `source_path`),
leaving the import path unchanged when `import_id` is set. Regression
test: a stem waveform job runs to completion through the manager with
the protocol stub worker.

### Export job parameters (backend → worker)

`_export_parameters_for(job)` rebuilds the request from the job's stored
parameters against the repository:

- `stems: [{stem_id, asset_id, role, display_name, source_path,
  source_hash, sample_rate, channel_count, frame_count}]` — equal
  `sample_rate` and `frame_count` across the selected stems is asserted
  (`EXPORT_ALIGNMENT`; the stem group is one synchronized set, §15.4
  "every exported stem begins at the same source origin");
  `channel_count` may differ per stem (mono outputs stay mono).
- `format`, `target_sample_rate` (null → source), `normalize`,
  `result_set_id`, and `download_filenames` per asset id — a pure,
  unit-tested sanitizer: `<safe label>-<set-short-id>-<rate/1000>k-<depth>.wav`
  with only `[A-Za-z0-9._-]`; the label is the sanitized display name
  with a role fallback; sanitation never touches the source track.
- Failure codes: `NO_STEMS`, `EXPORT_STEM_MISSING`, `EXPORT_ALIGNMENT`,
  `EXPORT_RESULT_SET`.

### Worker export runner (§15.3.4, 8–14)

Per selected stem, streaming passes over the raw f32le asset:

1. **Verify + measure** — size check, SHA-256 re-hash, and the joint
   peak (max |sample|) across the selected set; one pass per stem.
2. **Estimate disk** (§15.3.4) — Σ stems `out_frames × channels ×
   out_bytes` × `DISK_HEADROOM_FACTOR` + `MINIMUM_FREE_DISK_BYTES`
   before any write; insufficient → `EXPORT_DISK`.
3. **Clip rule** (§15.3.9–10) — integer outputs refuse when the joint
   peak exceeds the integer full-scale bound (`32767/32768` for s16,
   `8388607/8388608` for s24): `EXPORT_CLIPPING`, whose message names
   float32 and linked normalization as the remedies. Float32 output
   never refuses; linked normalization scales to 0.891 (−1 dBFS) and
   records the gain.
4. **Encode** (§15.3.12–13) — one ffmpeg pass per stem on the f32le
   input: filter chain `volume=<gain>dB` (linked normalization only)
   then `aresample=<target>:dither_method=triangular` for integer
   outputs (the float→int reduction dithers, §15.3.11) or
   `aresample=<target>` for float32 resampling only; encoder
   `pcm_s16le | pcm_s24le | pcm_f32le`; `-rf64 auto` so oversized WAVs
   fall back to RF64. Continuous resampling, no chunk staging.
5. **Verify** (§15.3.14) — ffprobe `-count_frames`: rate, channels,
   codec, decoded frames (equal-rate: exact; resampled: within
   `ENDPOINT_TOLERANCE_FRAMES`), plus the output SHA-256.
6. Progress stages `verifying_stems` → `encoding` → `verifying_export`.

### Publication and delivery (§15.3.14–16, §15.5)

- Migration 9: `export_artifacts` (per-stem row: `id, job_id,
  project_id, result_set_id, stem_id, audio_asset_id, role, format,
  sample_rate, channel_count, frame_count, normalized, gain_db, dither,
  sha256, byte_size, relative_path, download_filename, created_at`) and
  the `media_jobs` job-type CHECK extended with `export`.
- Publisher branch `_publish_export`: verify every staged file
  (existence, size, hash), move to `data/exports/<sha256>.wav`
  (hash-dedup: identical bytes reuse the file and never silently
  overwrite different bytes), insert artifact rows in one transaction
  with job completion. The manager verifies `ExportResult` like the
  other result models.
- `GET /api/v1/downloads/{artifact_id}` (§19.2): authenticated
  full-file stream (1 MiB chunks like `/assets/{id}/bytes`) with
  `Content-Type: audio/wav`, `Content-Length`, and
  `Content-Disposition: attachment; filename="…"` (RFC 5987
  `filename*` for non-ASCII).
- `GET /api/v1/projects/{project_id}/exports`: artifact list with job
  state, so completed exports stay re-downloadable after a reload.
- Reclaim protection (§9.5.6): `reclaim_storage` skips assets
  referenced by non-terminal export jobs; tested with a live export.
- Exports live under `data/exports/` — inside the protected `data`
  category, not the reclaimable separation cache; no `StoragePaths`
  change (relative `data/…` paths already resolve).

### Priority class

`EXPORT` gets its own class above background waveform work and below
import-critical: playback preparation (0) > import-critical (1) >
export (2) > waveform (3). The M2.12 three-class policy is extended
here; the priority test is updated.

### Frontend (§15.2, §15.3.16)

- `frontend/src/api/exports.ts`: `createExport` (per-submission
  `Idempotency-Key`), `listExports`, and `downloadExport` — an
  authenticated `fetch` → `Blob` → object URL → synthetic `<a download>`
  click → revoke (a plain `<a href>` cannot carry the bearer token).
  `waitForJob` (playback.ts) gains an optional `onProgress` callback.
- `ExportPanel` in `TrackStack`'s `.track-mode-bar` area (the active set
  and stems are already computed there): per-stem checkboxes (all on),
  format select (24-bit default), rate select (Original default /
  44.1 / 48 kHz), linked-normalization checkbox, Export button, progress
  text, artifact download list, and error surfacing (`EXPORT_CLIPPING`
  with the two remedies). Inline panel styled like the existing
  `.import-stream-dialog` (no dialog component exists in the tree).
- Tests: API module routes/errors, the download helper (fetch stub +
  anchor click), panel defaults/selection/clipping/download, and
  App-level wiring against the mocked client.

## Known deviations / notes

- The manager's import-required source check is a pre-existing defect
  for asset-sourced jobs (the M2.7 stem waveform path was created but
  never executes); fixed here with a regression test.
- `-rf64 auto` is verified by argv plumbing plus an RF64-header test
  that drives the same ffmpeg helper with `always` on a small file; a
  true >4 GiB run is out of scope locally.
- Dither behavior is asserted through the encoder chain (triangular on
  the float→int reduction) and a quantization sanity check; a
  perceptual test is out of scope.
- No new config keys; export artifacts follow the `data` category in
  the storage report.
- `tsc -b` has a 32-error pre-existing baseline; no new errors.
