# M3.4 plan — Run Beat This! and retain frame activations

Spec: `projectPlans/milestone3.md` §6 (M3.4). Fourth Milestone 3 work
package. Runs the isolated worker, validates the raw framewise arrays,
publishes immutable activation artifacts, and records durable run state.
No pulse decoding, API routes, or UI yet.

**Acceptance (§6):** the application retains auditable beat/downbeat
activation arrays aligned to source time and can cancel/fail without
damaging earlier results.

## Scope in / out

In:
- `rhythm/worker.py`: protocol-v2 worker with the `rhythm.activation.v1`
  capability, explicit local checkpoint, prepared PCM input, progress
  stages, cancellation, peak-memory reporting, and staged `.npy` outputs.
- Worker/backend progress stages for model load, inference, activation
  writing, and artifact validation.
- Backend `src/basseparate/rhythm/activations.py`: request validation,
  worker supervision, array validation (float32, 1-D, exact frame count,
  finite), deterministic artifact content hash, staged atomic
  publication, durable run updates, cancellation/failure cleanup.
- `rhythm_worker_command`/`rhythm_root` launcher with an explicit
  isolated interpreter.
- Tests: array/store validation, fake-worker success/failure/cancel, and
  a skipped-by-default real final0 CPU activation test.
- Evidence for the real run.

Out:
- Pulse decoding/confidence (M3.5).
- Automatic `RhythmResult` publication/branch creation (M3.6).
- Tempo/meter (M3.7–M3.9).
- Durable rhythm jobs/API/UI (M3.17); the service is the reusable
  boundary those will call.
- GPU qualification (the sandbox hides the GPU device nodes; approved device access required).
- Portable activation-file copy (M3.18).

## Decisions

1. **Storage layout:** `data/rhythm/activations/<artifact_id>/` with
   `beat.npy`, `downbeat.npy`, `manifest.json`; staging under
   `data/rhythm/.staging`. The M3.1 manifest is the authoritative
   metadata (source identity, frame mapping, hashes, semantics).
2. **The worker writes only arrays.** The backend validates and
   publishes; a worker crash or cancel cannot create a complete
   artifact.
3. **Raw logits are preserved unmodified.** No thresholding, no
   probability conversion, no JSON per frame. Confidence semantics stay
   uncalibrated (`kind=heuristic`, `calibrated=false` when decoded).
4. **Content hash is deterministic** over both array hashes plus model,
   adapter, and source identity. Artifact IDs are unique per run, so
   identical reruns produce distinct immutable artifacts with the same
   content hash.
5. **Cancellation is bounded by one inference call.** The worker checks
   before model load and after inference, removes staged arrays, and the
   supervisor stops the process if needed; no partial artifact is
   published.
6. **Progress uses the shared job stage vocabulary** extended with
   `loading_model`, `running_inference`, `writing_activations`,
   `validating_artifact`, and `decoding_pulses`. Durable job persistence
   of these stages arrives with the rhythm job wiring (M3.17), which must
   extend the database stage constraint at that point.
7. **CPU determinism is verified; GPU determinism is not claimed.**
   The worker records `deterministic: true` only for CPU.
