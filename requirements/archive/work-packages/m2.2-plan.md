## Phases

### Phase 1 — Plan + ledger

Write this plan; add the M2.2 section to `docs/implementation-status.md`;

### Phase 2 — Isolated analysis environment (§4.1)

- New `analysis/` project at the repo root with its own `pyproject.toml`:
  - `requires-python = ">=3.11,<3.12"` (same 3.11.11-class interpreter as
    the core app, uv-managed).
  - Dependencies: `demucs==4.1.0`, `torch==2.9.1` (resolved from the
    `pytorch-cu128` index → `2.9.1+cu128`), `soundfile` (audio loading;
    not declared by demucs).
  - `[[tool.uv.index]] pytorch-cu128` + `tool.uv.sources` so the lock
    pins the `+cu128` wheel explicitly.
  - No training extras, no dev tools — inference only (§4.1.5).
- `uv lock` + `uv sync --locked` inside `analysis/`.
- Record the resolved fingerprint (exact package list) in
  `docs/evidence/m2.2-analysis-environment.md`.
- The main `pyproject.toml` stays free of torch/demucs (§4.1.2); verify the
  main env imports nothing from them.
- Environment installation stays a separate, explicit step — never part of
  application startup (§4.1.8).

### Phase 3 — Qualification script + run (§4.2, §4.3)

- `analysis/qualify.py`, run with the analysis env's explicit interpreter
  path (§4.1.7):
  1. Per CUDA device: small tensor arithmetic, a representative
     `conv2d`, and an FFT (`torch.fft`) — §4.2.4–4.2.5.
  2. Per CUDA device: load `htdemucs` and run it on a short generated
     input (a few seconds of stereo audio) — §4.2.6.
  3. CPU path: same tensor/conv/FFT with compute threads limited to four
     (§4.3.2).
  4. Emit a JSON report (device, driver, versions, pass/fail, timings).
- Run it on both GPUs and the CPU; capture the reports.
- Record the results in `docs/evidence/m2.2-qualification.md`. Devices are
  marked usable only after the model test succeeds (§4.2.8).

### Phase 4 — Device records and selection (main backend, §4.4–4.5)

- `src/basseparate/domain/device.py`:
  - `QualificationStatus` enum (untested / qualified / failed).
  - `DeviceRecord`: GPU UUID, display name, total + free VRAM, runtime
    compatibility, last qualification result, unavailability reason.
  - Invariants: a qualified record must carry a qualification timestamp;
    a failed/unavailable record must carry a reason.
- `src/basseparate/devices.py` (no PyTorch import):
  - Discovery via `nvidia-smi --query-gpu=...` subprocess (driver-level
    facts only).
  - Free-VRAM refresh function (§4.4: refresh before a job starts).
  - Qualification store: JSON file under the storage data dir mapping
    device UUID → last result (timestamp, wheel fingerprint, pass/fail,
    detail).
  - `select_device(records, preferred_uuid)`:
    - preferred device wins if present **and qualified**;
    - else first qualified in default order (4080, then 5060 Ti — encoded
      as the discovery order, not hard-coded names);
    - else **no accelerator** — CPU is offered explicitly, never implicit;
    - a requested GPU that is missing/unqualified is reported, not
      silently substituted (§4.5).
- Unit tests with a stubbed `nvidia-smi` binary: discovery parsing,
  VRAM refresh, store round-trip, and every selection case (preference
  valid, preference stale, none qualified, no GPU at all).

## Notes

- The `htdemucs` checkpoint used for qualification is downloaded to the
  Hugging Face cache at run time. That is a developer qualification
  activity; the **bundled, hash-pinned** baseline is M2.3.
- One GPU at a time: the qualification script processes devices
  sequentially and frees CUDA context between them (no 32 GB pool, §4.5).
- The main-app import guard: a unit test asserts `torch`/`demucs` are not
  importable from the main env (they are not declared there).
