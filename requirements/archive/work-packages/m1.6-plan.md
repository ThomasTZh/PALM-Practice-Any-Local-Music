# M1.6 — Asset publication, hashing, and disk budgeting: implementation plan

Scope per `projectPlans/milestone1.md` §8. Gate B covers M1.4–M1.6.

**Acceptance property:** reopening reuses existing assets, and disk-space
failures leave a recoverable project.

## 0. Scope analysis — what M1.5 already delivered

Most of §8 landed as part of the M1.5 implementation (`b1d92d1`):

- **§8.1 Content-addressed storage** — PCM assets live at
  `data/assets/<hash>.pcm` (hash-based, app-generated). Two identities are
  maintained: the content hash (asset row) and the transformation key
  (representation row).
- **§8.2 Transformation key** — `compute_transform_key` v1 (canonical
  JSON) includes all seven canonical-decode elements: original-file hash,
  stream index, decoder-profile version, FFmpeg build identity, timestamp
  policy (`async-fill-trim`), output sample format (`f32le`), channel
  policy (`preserve`). Derived-playback keys (downmix matrix, target rate,
  resampler settings) are M1.7 scope.
- **§8.3 Publication sequence** — staging on the destination filesystem
  (`runtime/jobs/<job>/staging`, same volume as `data/assets`), metadata +
  size validation, chunked SHA-256, ffmpeg flushes/closes before
  validation, `shutil.move` into `data/assets/` (same-filesystem
  `os.rename`, atomic), asset metadata insert, project attach in one
  `BEGIN IMMEDIATE` transaction, job completed only after the references
  commit. Crash between rename and commit → unreferenced complete asset
  (`_ensure_pcm_asset` keeps the on-disk file and re-registers the row).
- **§8.4 Deduplication** — originals reused by source hash
  (`_ensure_original_asset`); canonical assets reused by content hash
  (`_ensure_pcm_asset`); never by filename/size. Waveform caches (§8.4.3)
  and playback representations (§8.4.4) do not exist yet in Milestone 1
  (M1.8 / M1.7).
- **§8.6 Cache cleanup boundary** — source and canonical assets are
  preserved (no GC exists); stale staging is removed only after recovery
  (`JobManager._cleanup_stale_staging` at startup); ambiguous recovery
  files are untouched.

Remaining gaps this work package closes:

1. **§8.5 Disk estimate** — the pre-flight check budgets only
   `1.25 × canonical PCM + 64 MiB floor`. The spec requires: retained
   original + canonical PCM + monitoring/playback representations +
   waveform caches + temporary publication overhead + a **2 GiB free-space
   reserve**. In Milestone 1 the representations and caches do not exist,
   so the budget is `original + 1.25 × PCM estimate + 2 GiB`.
2. **Acceptance test: disk-space failure leaves a recoverable project** —
   the failure mode exists (`InsufficientDiskSpaceError` →
   `INSUFFICIENT_DISK_SPACE`, checked before ffmpeg starts, no partial
   output) but is untested.
3. **Acceptance test: crash between file publication and DB commit** —
   the recovery path exists in `_ensure_pcm_asset` (file kept, row
   re-registered) but is untested.
4. **Dedup policy documentation** — §8.4.2 (reuse "only when the
   transformation key matches") is satisfied by the stronger content-hash
   rule; record why.

## 1. Disk budget — `src/basseparate/media/decode.py`

- New constant `PUBLISH_RESERVE_BYTES = 2 * 1024**3` (2 GiB).
- `_required_free_bytes(estimated_duration_seconds, sample_rate,
  channel_count, retained_original_bytes)`:
  `max(1.25 × PCM estimate + retained original + 2 GiB reserve, 64 MiB
  floor)`. PCM estimate uses the probe duration when available (the
  conservative direction: a missing estimate only lowers the budget, and
  the reserve dominates).
- `decode_canonical` passes `source_path.stat().st_size` as the retained
  original size.

## 2. Dedup policy note — `src/basseparate/jobs/publisher.py`

`_ensure_pcm_asset` docstring: content-hash reuse is the stronger form of
the transformation-key rule — for a deterministic pipeline, identical
bytes imply an identical transformation key.

## 3. Tests

- `tests/unit/test_decode.py` — `TestDiskBudget`:
  - budget = `1.25 × PCM + original + 2 GiB` (exact arithmetic);
  - no duration estimate → original + reserve (above the floor);
  - fake `shutil.disk_usage` (10 MiB free) → `InsufficientDiskSpaceError`
    raised before ffmpeg starts, no output file created.
- `tests/integration/test_job_manager.py` —
  `TestDecodeCompletion::test_crash_between_publish_and_commit_recovers`:
  decode to completion; delete the asset + representation rows (file stays
  on disk); re-decode → same content hash, a fresh asset row, the on-disk
  file byte-identical (reused, not re-written), project ready with the new
  canonical asset id.

## Confirmed design points

- The 2 GiB reserve is a module constant in the decode engine (the worker
  process owns the pre-flight check); 369 GB free on this box, so real
  ffmpeg tests are unaffected.
- Staging (`runtime/jobs`) and assets (`data/assets`) are both under the
  storage root → same filesystem → `shutil.move` is an atomic rename; no
  cross-device fallback needed.
- No API surface changes; no schema changes; no frontend changes.
