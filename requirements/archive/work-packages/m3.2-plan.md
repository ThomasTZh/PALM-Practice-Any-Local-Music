# M3.2 plan — Integrate the Beat This! runtime and model registry

Spec: `projectPlans/milestone3.md` §4 (M3.2). Second Milestone 3 work
package. Establishes the isolated rhythm runtime, verified model
registry, explicit install/offline-import boundary, and CPU
qualification. No inference pipeline, activation publication, or
rhythm API/UI.

**Acceptance (§4):** `final0` can be installed explicitly, qualified,
and run with external network access disabled; existing projects remain
usable with the model absent.

## Scope in / out

In:
- `rhythm/`: dedicated uv project (Python 3.11, torch/torchaudio
  2.9.1+cu128, `beat-this==1.1.0`), own lockfile, explicit interpreter.
- Registry entries for `beat_this_final0` and `beat_this_small0` with
  verified sizes, SHA-256, upstream revision, licenses, preprocessing,
  output semantics, adapter version, and capability.
- Explicit network install boundary: offline-mode gate, staged
  download, byte progress, cancellation, exact size/hash verification,
  atomic publication, provenance record; no torch imports.
- Offline bundle import with manifest identity and re-hashing.
- CLI (`basseparate models list|install|verify|import-bundle`) and a
  non-mutating `rhythm-models` doctor check.
- CPU qualification script and evidence for both presets.

Out (later packages):
- Beat This! inference worker, activation artifacts, and publication
  (M3.3–M3.4).
- Durable download job/worker, API routes, and settings UI (M3.17);
  this package provides the reusable boundary those call.
- GPU qualification (the sandbox hides the GPU device nodes; approved device access required); no GPU result is claimed.
- Automatic rhythm results, decoder, tempo/meter (M3.5–M3.9).

## Decisions

1. **Separate environment, not the Demucs env.** `rhythm/.venv` pins
   `beat-this==1.1.0` and its own torch/torchaudio. The application and
   Demucs environments stay untouched; no torch import at backend
   startup.
2. **Upstream pins.** Code revision tag `v1.1.0`
   (`ad7974846029...`); PyPI wheel SHA-256 recorded. Checkpoints come
   only from the official CPJKU cloud space; the server SHA-1 was
   checked and the registry pins SHA-256.
3. **Model IDs** are `beat_this_final0` and `beat_this_small0`; the
   upstream preset names (`final0`, `small0`) remain separate fields.
4. **Install boundary is explicit and offline-gated.** Online install
   raises before network access while offline mode is active; the CLI
   prints the license and requires `--yes` or the interactive
   confirmation. The service is injectable for tests and has no worker
   or API coupling yet.
5. **Bundle identity is not trusted.** Offline import requires a
   `manifest.json` matching model ID, filename, size, and SHA-256, and
   re-hashes the checkpoint while copying.
6. **Qualification is per model/device.** The script passes an explicit
   local checkpoint path (never a preset name), disables Hugging Face /
   Transformers offline retries before torch import, bounds CPU
   threads, checks finite and deterministic outputs, and records
   geometry/timing/RSS.
7. **No hidden downloads.** Registry/model resolution in the app only
   reads the managed store and reports missing models; `doctor` never
   fetches.

## Known boundaries

- GPU qualification is unperformed (no device nodes in the sandbox); CUDA capability
  is recorded but not claimed.
- The durable install job, API routes, and settings UI land in M3.17.
  Until then the explicit CLI action is the installation path.
- Inference and activation artifacts are M3.4.
- The runtime lock currently installs CUDA-enabled wheels; a CPU-only
  wheel set is not provided. This keeps the same verified CUDA line as
  the Demucs environment and still runs on CPU without a driver.
