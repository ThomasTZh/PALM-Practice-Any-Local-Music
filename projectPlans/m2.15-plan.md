# M2.15 plan — Safely save portable projects (spec §17)

Build the save side of the portable project workflow: capture the working
project at its current revision, build a complete, self-contained
`.basseparate` archive (project-only DB + essential assets + optional
caches + provenance + manifest), and publish it atomically to managed
storage as a downloadable artifact. The M2.14 format layer (plan, DB
builder, manifest models) is reused as-is except for one extension
documented below.

This package is file I/O only. It introduces no media jobs, no DSP, and
no new worker dispatch; the save runs synchronously in the FastAPI
threadpool. Separation-job scheduling and analysis-worker concerns stay
in M2.17.

## Scope guardrails

- Monitoring/diagnostics only: the save pipeline never writes to the
  source project DB, source assets, annotations, or the working store
  beyond reading. Its writes are the staging file, the published
  artifact file, and the `portable_artifacts` rows.
- No source/annotation/storage mutation: the portable DB is built from a
  read-only snapshot (M2.14 `build_portable_database`); assets are
  stream-copied, never rewritten.
- Cancellation and failure never destroy the last valid file: the
  published artifact is only replaced by a fully verified new one via
  atomic `os.replace`. A failed save deletes only its own staging file.
- In-progress runs are excluded: the plan is computed from the committed
  working state; running jobs' intermediate outputs are not part of the
  closure.
- Contract regeneration is required this time (new API surface).

## Design

### Synchronous API, not a media job

Portable save is pure file I/O (zip + hash + copy). Running it as a media
job would touch the job manager, worker dispatch, and progress reporting
(M2.17 territory) for no benefit. The route is a plain `def` endpoint, so
FastAPI runs it in the threadpool. A save of a normal-sized project takes
seconds; the browser polls nothing, it gets one 201 response.

### Package layout

```
src/basseparate/domain/portable.py      # PortableArtifact model
src/basseparate/portable/writer.py      # archive writer (zip + hashing)
src/basseparate/portable/save.py        # save pipeline (staging → verify → publish)
src/basseparate/storage/repository.py   # PortableArtifactRepository (added)
src/basseparate/storage/db.py           # migration 10 (added)
src/basseparate/api/portable_routes.py  # save / list / download routes
frontend/src/api/portable.ts            # API client
frontend/src/tracks/PortableSavePanel.tsx  # UI panel
```

### Storage layout

- Managed publication: `data/portable/<project_id>/<saved_revision>-<sha256[:12]>.basseparate`
  (the archive's own sha256 is in the filename, mirroring M2.13's
  `data/exports/<sha256>.wav`). `relative_path` in the artifact row
  carries the `data/` category prefix, so `StoragePaths.resolve_asset_path`
  resolves it like every other data-root path.
- Staging: `data/portable/.staging/<uuid>.basseparate` — same filesystem
  as the publication target, so the final `os.replace` is atomic.
- The DB snapshot lives in a `tempfile.TemporaryDirectory` (M2.14
  builder) and is removed with it.

### Domain model (`domain/portable.py`)

```python
class PortableArtifact(BaseModel):  # frozen
    id: Uuid
    project_id: Uuid
    saved_revision: int = Field(ge=0)
    sha256: Sha256Hash
    byte_size: int = Field(ge=1)
    relative_path: str              # portable/<project_id>/<file>.basseparate
    download_filename: str          # <project-name>-r<revision>.basseparate
    created_at: UtcTimestamp
```

Mirrors the `ExportArtifact` shape. `relative_path` is relative to the
data root; the download filename is user-friendly and independent of the
managed name.

```sql
CREATE TABLE IF NOT EXISTS portable_artifacts (
    id                TEXT PRIMARY KEY,
    project_id        TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    saved_revision    INTEGER NOT NULL,
    sha256            TEXT NOT NULL,
    byte_size         INTEGER NOT NULL,

```

`DATABASE_SCHEMA_VERSION` → 10 in `src/basseparate/__init__.py`. The M2.14
portable DB builder asserts `user_version == 9`; that baseline becomes 10
(the builder reads whatever the source DB reports, so the portable
archive carries v10 from now on). Tests asserting the v9 baseline are
updated in the same change.

### Repository (`PortableArtifactRepository`)

Synchronous, same `_open`/transaction style as `ExportArtifactRepository`:

- `publish(artifact) -> PortableArtifact` — insert the row.
- `delete_older(project_id, keep_ids)` — retention: remove rows (and
  their files, handled in save.py) not in `keep_ids`.
- `get(artifact_id) -> PortableArtifact | None`
- `list_for_project(project_id) -> list[PortableArtifact]` (newest first)
- `latest_for_project(project_id) -> PortableArtifact | None`

### Writer (`portable/writer.py`)

```python
class PortableWriteError(ValueError): ...

def write_portable_archive(
    plan: PortablePlan,          # already reduced (see save.py)
    db_snapshot: Path,
    paths: StoragePaths,
    destination: Path,
    saved_at: datetime,
) -> PortableManifest:
```

Member order (deterministic):

1. `project.sqlite` — the portable DB snapshot, stored.
2. `assets/<asset.relative_path>` — each plan asset, stored, in
   `plan.assets` order (already sorted by the closure builder).
3. `caches/waveforms/<source_hash>/...` — each waveform cache directory
   recursively, files sorted by relative path, stored.
4. `provenance/separation_runs.json` — deflate, via `writestr`
   (`separation_runs_payload(plan.separation_runs)`).
5. `provenance/model_manifests.json` — deflate, via `writestr`.
6. `manifest.json` — deflate, via `writestr`, **last**.

Per-member streaming write (large assets must not be buffered):

```python
info = zipfile.ZipInfo(name, date_time=_zip_time(saved_at))
info.compress_type = compression_for(name)
info.external_attr = 0o644 << 16
with zf.open(info, "w") as dest, source.open("rb") as src:
    h = hashlib.sha256(); size = 0
    while chunk := src.read(1 << 20):
        dest.write(chunk); h.update(chunk); size += len(chunk)
```

- `ZipFile(destination, "w", allowZip64=True)`.
- All `ZipInfo.date_time` values are derived from `saved_at`, so the
  archive bytes are deterministic for a given input set (verified by
  test: two writes of the same store → identical sha256).
- A missing asset file inside the writer raises `PortableWriteError`
  (defence in depth; save.py checks before calling).
- `PortableManifest` is built from the collected `(name, sha256, size,
  compression)` tuples plus plan metadata and written last.
- `manifest.members` lists every member **except** `manifest.json`
  itself (the manifest cannot hash itself; the M2.16 verifier requires
  the archive to contain exactly `{manifest.json} ∪ member names`).
  The `ManifestMember` docstring is updated to say so.
- After close: `os.fsync` the file descriptor, then return the manifest.

### Save pipeline (`portable/save.py`)

```python
class PortableSaveError(Exception):
    def __init__(self, code: str, message: str, details=None)

class PortableSaveMissingAsset(PortableSaveError)   # code SAVE_ASSET_MISSING
class PortableSaveNoSpace(PortableSaveError)        # code SAVE_NO_SPACE

def perform_portable_save(
    db_path: Path,
    paths: StoragePaths,
    project: ProjectRow,
    artifacts: PortableArtifactRepository,
) -> tuple[PortableArtifact, PortableManifest]:
```

Steps, mapped to §17.1:

1. **Flush pending manual commands** — architectural no-op: project
   commands are durably applied at apply-time (M1.x command pipeline);
   there is no unapplied queue to flush. Documented in the code.
2. **Capture revision** — `project.revision` from the project row passed
   in by the route (single read; the route opens the project first).
3. **Compute plan** — `compute_portable_plan`. The plan's
   `asset_ids`/`result_set_ids` are the "temporary references" for the
   save: held in memory for the duration of the request so nothing the
   save reads can be concurrently redefined. No global pin registry (the
   store is single-process and the save is the only writer to
   `data/portable/`).
4. **Check file presence** — for every plan asset, resolve
   `paths.resolve_asset_path(a.relative_path)`; if the file is missing:
   - essential → raise `PortableSaveMissingAsset` (list the files);
   - optional → add to `excluded` set.
   Also check each waveform cache directory exists (missing cache dir is
   treated as an empty cache, not an error — caches are rebuildable).
5. **Reduce the plan** — `plan_with_exclusions(plan, excluded)` returns
   a new `PortablePlan` with the excluded assets removed from
   `assets`, `asset_ids`, and `waveform_caches` entries. Essential
   exclusion never happens (step 4 raised instead).
6. **Build portable DB** — `build_portable_database(db_path,
   project_id, snapshot, excluded_asset_ids=excluded)`. The builder
   gains one optional parameter (default empty) that filters
   `assets`, `representations`, and `waveform_caches` rows. The
   `PortablePlan` passed to the writer is the reduced one, so the DB
   rows and archive members agree.
7. **Estimate size** — sum of db snapshot size + asset byte counts +
   cache dir sizes + JSON sizes + ~1 KiB zip overhead per member.
   Check `shutil.disk_usage(staging_dir).free >= estimated`; else raise
   `PortableSaveNoSpace`.
8. **Stage + write** — create `data/portable/.staging/` if needed,
   `uuid4` staging name, run the writer.
9. **Verify the staged archive** — reopen with `zipfile.ZipFile`:
   `testzip()` (CRC check), then re-hash every member and compare with
   the manifest's `sha256`, verify the member set equals
   `{manifest.json} ∪ names`, and parse + validate `manifest.json` with
   `PortableManifest.model_validate_json`. Any mismatch →
   `PortableSaveError(SAVE_VERIFY_FAILED)`.
10. **Archive sha256** — `sha256_file(staging)` (reused from
    `media/preparation.py`).
11. **Retention** — `artifacts.list_for_project(project_id)`: keep the
    newest previous artifact (the current one is not recorded yet),
    delete older rows + their files (missing files tolerated).
12. **Atomic publish** — destination
    `data/portable/<project_id>/<revision>-<sha12>.basseparate`
    (create parent dir); `os.replace(staging, destination)`.
13. **Flush** — best-effort `os.fsync` on the publication directory fd.
14. **Record** — `artifacts.publish(PortableArtifact(...))`.
15. **Return** — the artifact.

Failure semantics: the whole staging phase (steps 8–10) is wrapped; on
any exception the staging file is deleted and the error propagates.
Published artifacts, previous retained artifacts, the source store, and
the working DB are never touched. No partial rows: the artifact row is
written only after a successful publish.

### `excluded_asset_ids` in the M2.14 builder

`build_portable_database` gains
`excluded_asset_ids: frozenset[str] = frozenset()`. The `assets`,
`representations`, and `waveform_caches` `INSERT ... SELECT` statements
add `AND id NOT IN (...)` / `AND asset_id NOT IN (...)`. Everything else
is unchanged; the default keeps M2.14 behaviour for other callers.

### Routes (`api/portable_routes.py`)

- `POST /api/v1/projects/{project_id}/portable-saves`
  - `def` (threadpool). `Idempotency-Key` header per the M2.13 pattern
    (body is empty; body_hash = hash of b"").
  - 404 `PROJECT_NOT_FOUND` if the project is missing.
  - 201 with the artifact: `{ id, project_id, saved_revision, sha256,
    byte_size, download_filename, download_url, created_at }`.
  - `SAVE_ASSET_MISSING` → 409 with the missing file list in `details`.
  - `SAVE_NO_SPACE` → 507.
  - Other `PortableSaveError` → 500 with the code.
  - Idempotent replay returns the cached payload with the original
    status.
- `GET /api/v1/projects/{project_id}/portable-saves`
  - 200 with the artifact list (newest first), 404 for unknown project.
- `GET /api/v1/portable-downloads/{artifact_id}`
  - Streaming `StreamingResponse` mirroring `_iter_file_chunks` from
    `export_routes.py`; `Content-Type: application/zip`,
    `Content-Disposition: attachment; filename="<download_filename>"`,
    `X-Content-Sha256`, `X-Content-Size`. 404 for unknown artifact or
    missing file (file missing with a row present → 410-style 404 with
    code `PORTABLE_ARTifact_FILE_MISSING` — the row remains for
    reporting; the user re-saves).

Router is registered in `app.py` next to `export_router`.

## Tests

Backend:

- `tests/unit/test_portable_writer.py` — seed a small store (reuse the
  M2.14 seed helpers), write an archive, then:
  - member set and order; per-member sha256/size match the manifest;
  - compression types per policy (sqlite/assets stored, JSONs deflate);
  - manifest excludes itself and validates via the model;
  - determinism: two writes of the same inputs → identical sha256;
  - missing asset file → `PortableWriteError`.
- `tests/unit/test_portable_plan_exclusions.py` —
  `plan_with_exclusions` removes assets, ids, and cache entries.
- `tests/integration/test_portable_save.py` — full pipeline against a
  temp data root:
  - save → artifact row + file at the managed path + sha256/size match;
  - re-save → retention keeps exactly one previous;
  - essential asset file deleted → `PortableSaveMissingAsset`, no
    staging file left, no new row, previous artifact intact;
  - optional asset file deleted → excluded from archive members and
    portable DB rows, save succeeds;
  - no-space (monkeypatched disk_usage) → `PortableSaveNoSpace`.
- `tests/integration/test_portable_routes.py` — TestClient:
  - POST → 201 + artifact; replay with same Idempotency-Key → identical

## Acceptance (from §17)

- Saving produces a complete, self-contained archive that M2.16 can open
  without the original store.
- The published file is replaced atomically; a failed or interrupted
  save never destroys the last valid file.
- One previous artifact is retained; older ones are reclaimed.
- The UI shows the saved revision, newer unsaved changes, and the
  download link (§17.5).
- In-progress runs are not part of the archive; the archive reflects the
  committed working state at the captured revision.
