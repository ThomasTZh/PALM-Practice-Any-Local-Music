# M1.14 plan — Synchronized readout and follow-playhead

Spec: `projectPlans/milestone1.md` §16. Frontend-only. Makes the time
readout and the waveform playhead track **audible** playback without
drift: worklet anchors at ~20 Hz, an output-timestamp-based audible
position estimate with retained transport segments, an rAF-driven
playhead that does not churn React state, and page-follow behavior
(80 % trigger / 20 % landing) with a persisted, visible follow control.
No backend changes.

Out of scope: chord/note/bar readouts (forbidden in Milestone 1,
§16.3), looping and markers (M1.15).

## 2. Position anchors (§16.1)

- Cadence: the worklet posts an anchor every
  `anchorEvery = max(1, round(sampleRate / 20))` frames (2400 at
  48 kHz ≈ 20 Hz), not per audio block. The existing
  `anchorEveryFrames` constructor option stays (tests).
- Payload: `{ type: 'anchor', frame, time, generation, paused }` —
  transport generation, context render time, source frame, playback
  state (`paused`), and the buffered extent is reported alongside on
  the same cadence (existing `reportBuffered`).
- The transport keeps owning the state machine; the worklet's
  `paused` is informational (consistency, not control).

## 3. Audible-position estimate (§16.2)

- `TransportContextLike` gains
  `getOutputTimestamp?(): { contextTime: number; performanceTime: number } | null`.
  Real browsers: available. Test fakes: absent (fallback path).
- **Segments**: the transport retains
  `segments: Array<{ startContextTime, startFrame, generation }>` —
  pushed in `flushBookkeeping` (every seek/stop/rebind) and in
  `rebind`. Bounded to 16 entries. Mapping a context time to a frame
  always uses the newest segment whose `startContextTime ≤ t`; times
  before the newest segment's start stay in the older segment (no
  wrap to negative offsets).
- **`getAudiblePosition()`** (public; `position` getter delegates):
  1. No target → parked frame; `contextLost` → retained frame
     (unchanged).
  2. Frozen states — `paused`, `buffering`, `preparing`, `suspended`,
     `ended` → the last acknowledged anchor position, **no
     extrapolation** (§16.2.6).
  3. Active states (`playing`, `seeking`):
     `t = getOutputTimestamp()?.contextTime ?? max(0, currentTime −
     FALLBACK_OUTPUT_LATENCY_SECONDS)`.
     **Documented fallback estimate: 0 s** — without the output
     timestamp API the context time is assumed to be the audible
     time (constant + comment; keeps the M1.13 extrapolation
     behavior for environments without the API).
  4. Map `t` through the segment list (clamped to
     `[segment.startFrame, target.frameCount]` — §16.2.5), then
     `projectPosition` + `clampToDuration` (unchanged).
- The readout text updates at the anchor cadence (~20 Hz, §16.5.4)
  via the existing `onPosition` path; no UI timer drives playback
  (§16.5.6).

## 4. Readout (§16.3)

- Existing `MM:SS.mmm / MM:SS.mmm` readout unchanged (now
  audible-based).
- Source inspector (`App.tsx` Source section `<dl>`) gains a
  `Frame` line with the exact source frame (project frames are
  source frames in Milestone 1 — 1:1 rate).

## 5. Playhead drawing (§16.5)

- `WaveformEditor` props: `playheadFrame: number` **removed**;
  `playheadSource?: { getPosition: () => number; isPlaying: () => boolean }`
  added.
- One rAF loop runs while the editor is `ready` with a viewport:
  each frame reads `getPosition()`, converts to x, and redraws only
  the per-lane playhead canvases when x moved ≥ 0.5 px. No playhead
  value is stored in React state per update (§16.5.5). Interpolation
  (context-time extrapolation) happens in the transport — the UI only
  displays it (§16.5.3). The loop never calls into the transport for
  control (§16.5.6).
- `playheadOutside` (drives the "Return to playhead" button) is a
  boolean state written only on change (React bails out on equal
  values).
- Paused seeks, suspension, and context-loss redraws all flow through
  the same loop (position changes are picked up on the next frame).

## 6. Follow-playhead (§16.4)

- Default: page-follow on (persisted value wins when present).
- While following and `isPlaying()`: the viewport stays still while
  the playhead x < 80 % of the width; at ≥ 80 % it advances so the
  playhead lands at 20 % (`startFrame = frame − 0.2 · visible`,
  clamped). One `setView` per page advance (low frequency).
- Manual navigation (pan, zoom, overview drag, wheel) suspends
  following (existing `applyViewChange` behavior).
- Visible control: a "Follow playhead" checkbox in the editor
  toolbar re-enables/disables immediately; "Return to playhead"
  centers on the playhead **and** re-enables follow.
- Persistence: `localStorage['basseparate.playheadFollow']` =
  `'true' | 'false'` (global preference, read on mount, written on
  change; storage errors are non-fatal, matching the amplitude
  persistence pattern).

## 7. Panel wiring

- `PlaybackPanel` gains `registerPlayhead?: (source: { getPosition:
  () => number; isPlaying: () => boolean } | null) => void`. An effect
  registers a source whose functions read `transportRef.current`
  (`getPosition` → `transport.getAudiblePosition()`, `isPlaying` →
  state ∈ {playing, seeking}) and deregisters on unmount.
- `ProjectView` holds the source in state (set at most once per
  mount — the functions are stable) and passes it to
  `WaveformEditor`.
- The 20 Hz text readout keeps using the panel's `position` state
  (`onPosition`), which is the spec's ~20 Hz text update.

## 8. Test matrix

`worklet-core.test.ts`:

1. Anchors land every `rate / 20` frames at 48 kHz (2400), not every
   480; the `anchorEveryFrames` override still wins.
2. Anchor payload carries `generation` and `paused` (false while
   playing, true after a pause).

`transport.test.ts` (fake context, no `getOutputTimestamp` →
fallback path; one rig variant adds the API):

3. Fallback: with no API, active-state position extrapolates from
   `currentTime` (zero documented latency) — existing M1.13
   expectations hold.
4. API path: with `getOutputTimestamp()` returning
   `contextTime = currentTime − 0.1`, the audible position lags the
   scheduled one by 0.1 s · rate.
5. Segment retention: play → seek → the position maps through the new
   segment; a context time from *before* the seek clamps to the old
   segment's range (no negative offsets, no wrap).
6. Frozen: while paused / buffering / suspended the position stays at
   the last anchor as context time advances.

`WaveformEditor.test.tsx` (manual rAF scheduler stub; canvas stubs
already exist):

7. The rAF loop draws the playhead at `getPosition()`'s frame (x
   advances as the fake source advances); no React state churn
   (render count stable across frames).
8. Follow: with the playhead at ≥ 80 % of the width and following,
   the viewport advances and the playhead lands at ~20 %; below 80 %
   the viewport is untouched.
9. Manual zoom/pan suspends follow; the "Follow playhead" control
   re-enables it; the preference persists to `localStorage` and
   survives a remount (default true when unset).
10. "Return to playhead" centers on the playhead and re-enables
    follow (carried over from M1.11, new 80/20 model).

`playback-panel.test.tsx` (App-level, rAF stubbed):

11. The Source inspector shows the exact frame and it follows an
    anchor (0 → 24 000 → `0:00.500` and `Frame 24000`).

## 10. Risks / notes

- Removing the `playheadFrame` prop changes the editor's public
  surface; `WaveformEditor.test.tsx` is updated in the same phase so
  the gate stays green per phase.
- `getOutputTimestamp` is absent in jsdom and in the test contexts —
  the fallback path (zero documented latency) is what tests exercise
  by default; the API path is covered by one rig variant.
- The rAF loop must be deterministic in tests: the test harness
  stubs `requestAnimationFrame` with a manual scheduler (no real
  timers) and drives frames explicitly.
- Follow page advances must not fight the user: a `setView` from the
  follow loop counts as a programmatic change and must **not**
  suspend follow (only user-initiated `applyViewChange` does).
- The 20 Hz anchor cadence also halves the shared-path `buffered`
  feedback rate; chunk cadence is 1 s, so 20 Hz remains ample for
  flow control.
