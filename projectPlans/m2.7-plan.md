# M2.7 plan — Analysis caching and version retention

**Status (2026-10-13):** Phases 1–5 done and verified (ruff + mypy
clean; 198 passed across affected suites). Next: Phase 6 (evidence +
close). All changes uncommitted. See `docs/implementation-status.md`
M2.7 section for the full resume state.

Spec: `projectPlans/milestone2.md` §9. M2.6 turns a completed staged
run into **published, validated stem assets + an immutable result
set**. This work package makes separation results **cacheable and
retained**: a deterministic cache key per separation request, a
lookup that returns an existing valid result before scheduling,
coalescing support for identical pending requests, effective-parameter
keying after memory recovery, an **undoable active-result-set
selection** persisted with the project, and a 50 GiB configurable
storage policy with pinning, a reclaimable-size report, and explicit
policy-compliant cleanup. No new API routes (the existing command
endpoint exposes the new op; storage-report/cleanup routes are M2.17),
no scheduler wiring (M2.17 consumes the lookup/coalescing primitives),
no frontend (M2.8).

## Resolved facts (codebase map, 2026-10-11)

- **No cache policy exists in code yet.** M1's cache boundary
  (milestone1.md §8.6) is "preserve source and canonical assets;
  permit explicit deletion of rebuildable waveform/playback caches; no
  automatic broad GC". §9.5.1's "existing 50 GiB configurable cache
  policy" is therefore introduced by this work package: a new
  `cache_limit_bytes` config field (default 50 GiB).
- **Command/undo system (M1.15):** `domain/commands.py` defines
  `ProjectCommandOp`, a discriminated union of frozen op models;
  `ProjectRepository.apply_command` validates the base revision,
  applies the op in memory (`_apply_op`), re-validates the full
  `ProjectRecord`, records one `project_history` entry
  (`before_json`/`after_json` snapshots of **markers + working
  state**), clears the redo branch, and bumps the revision.
  `_move_history` restores a snapshot on undo/redo. `HISTORY_EXCLUDED_TYPES`
  opts ops out of history. Adding an op = add the model, extend the
  union, handle it in `_apply_op`; undo works automatically when the
  changed state lives in the snapshot (markers/working state).
- **`WorkingState`** (`domain/project.py`) is the snapshot carrier:
  selection, viewport, channel display, monitoring volume, last
  position, follow playhead. It is stored as a JSON column on
  `projects`; adding a defaulted field needs **no migration**.
- **Separation records (M2.1/M2.5/M2.6):** `SeparationRun` already
  carries `requested_parameters` **and** `effective_parameters`
  (memory-recovery audit pair), `random_seed`, `device_type`,
  `gpu_uuid`, `engine_version`, `adapter_version`,
  `model_manifest_id`/`model_manifest_hash`, `input_transform_hash`;
  `SeparationResultSet` carries `source: SourceIdentity`,
  `reference_mix: ReferenceMixIdentity`, `output_sample_rate`,
  `output_channel_count`, stems. Neither has a cache key (gap).
- **`models/registry.py`** pins every artifact's sha256 per manifest
  (`ArtifactSpec.sha256`); `models/bundle.py::verify_bundle` checks
  them. The key needs "model manifest and every weight hash" →
  manifest id + the sorted artifact-hash mapping (caller resolves the
  manifest; the key function stays pure).
- **Schema:** `DATABASE_SCHEMA_VERSION = 7` (`src/basseparate/__init__.py`);
  `storage/db.py` has a registered-migration pattern
  (`register_migration(n, fn)`, each migration one `BEGIN IMMEDIATE`).
  `separation_runs` and `separation_result_sets` are JSON-blob tables
  with query columns (`status`, `requested_mode`, `result_set_id`,
  `validation_status`).
- **Storage layout (`storage/paths.py`):** assets live at
  `data/assets/<sha256>.pcm`; the model bundle lives outside
  `data/` at `models/<bundle_prefix>/` (M2.3) — model storage is
  naturally countable separately. `project_assets` links
  (project, asset, role) with `AssetRole.STEM` rows for every
  published result set (M2.6).
- **Publication (M2.6):** `media/publication.py::publish_separation_result`
  is the single place a result set is created; it takes the run, the
  `SourceIdentity`, the reference path, and the output profile —
  everything a cache key needs except the manifest artifact hashes
  and the profile parameters, which the caller (M2.17) resolves.
- **Tests:** `tests/unit/test_commands.py` +
  `tests/unit/test_repository_commands.py` (command op patterns),
  `tests/integration/test_migration_m2.py` (migration patterns),
  `tests/integration/test_separation_repository.py` +
  `tests/integration/test_publication.py` (M2.6 fixture patterns:
  synthetic staged runs, DC signals).

## Design

### Cache key (§9.1) — `src/basseparate/media/separation_cache.py`

Pure, deterministic, versioned:

```python
CACHE_KEY_VERSION = "v1"

def compute_cache_key(
    *,
    source: SourceIdentity,            # canonical asset hash
    reference_mix: ReferenceMixIdentity,
    downmix: DownmixSpec | None,       # stream/downmix identity (§6.1)
    model_manifest_id: str,
    model_artifact_hashes: Mapping[str, str],  # every weight hash
    engine_version: str,
    adapter_version: str,
    mode: SeparationMode,
    requested_parameters: dict[str, Any],
    effective_parameters: dict[str, Any] | None,
    random_seed: int,
    device_type: DeviceType,
    output_sample_rate: int,
    output_channel_count: int,
) -> str  # sha256 hex
```

- Payload = versioned dict; `parameters` =
  **`effective_parameters` when present, else
  `requested_parameters`** (§9.3: a memory-recovery result is stored
  under the key of the profile it actually used, never mislabeled as
  the requested one). The M2.5 run record already carries the input
  resampling profile, normalization profile version+hash, outer-window
  settings, internal segment/overlap, shift count, and precision
  flags inside these parameter dicts, so §9.1's per-item list is
  covered by: source/reference hashes, downmix spec, manifest id +
  artifact hashes, engine/adapter versions, the (effective)
  parameters, seed, and the output transform profile
  (`output_sample_rate` + `output_channel_count`).
- `device_type` is the **execution profile** (cpu vs cuda), not a
  specific GPU identity: the float32/TF32 pin (M2.5) makes results
  reusable across devices of the same profile. `gpu_uuid` is
  deliberately excluded.
- Canonical serialization: `json.dumps(payload, sort_keys=True,
  separators=(",", ":"), ensure_ascii=True)` → sha256. The
  `CACHE_KEY_VERSION` prefix makes any payload-format change a clean
  miss (old keys simply stop matching) instead of a silent
  collision.

### Cache-key persistence — schema v8

- `SeparationRun.cache_key: Sha256Hash | None = None` and
  `SeparationResultSet.cache_key: Sha256Hash | None = None`
  (defaulted → pre-v8 rows deserialize unchanged).
- Migration 7→8: `ALTER TABLE separation_runs ADD COLUMN cache_key
  TEXT`, same for `separation_result_sets`, plus indexes
  `(project_id, cache_key)` on both. `DATABASE_SCHEMA_VERSION = 8`.
- `create_run` / `publish_result_set` copy the key from the record
  into the query column. `publish_separation_result` gains an
  optional `cache_key: str | None = None` parameter and stamps it on
  the result set (and the completed run) it publishes; M2.17 computes
  it via `compute_cache_key` at scheduling and publication time.

### Cache lookup (§9.2)

Repository (new `SeparationRepository` methods):

- `find_valid_result_set(project_id, cache_key)` — the newest
  `validation_status = 'valid'` result set for (project, key).
- `find_active_run(project_id, cache_key)` — a `queued`/`running` run
  for (project, key); **cancelled/failed/interrupted runs never
  match** (§9.2.8).

Service `lookup_cached_result(*, project_id, cache_key, asset_dir,
repository, verify_hashes=False) -> SeparationResultSet | None`:

1. Look up the matching valid result set (§9.2.1).
2. Resolve every stem asset (+ the bass residual when present); each
   file must exist **with exactly the expected byte size**
   (`frames × channels × 4`) — a short/partial file is a miss, never
   a hit (§9.2.2, §9.2.5).
3. When `verify_hashes` (integrity in doubt), re-hash each file and
   compare to the asset `content_hash`; a mismatch is a miss
   (§9.2.3). The default fast path skips full re-hashing — the
   content-addressed filename plus size check is the normal
   guarantee.
4. Return the result set on a valid hit (§9.2.4).

§9.2.6–7 (coalescing identical concurrent requests; publishing only
one result for an identical pending request) are scheduler policies:
M2.17's scheduler calls `find_active_run` before creating a job and
`lookup_cached_result` before that; this work package provides the
primitives and the "one completed result" property falls out of
`publish_result_set`'s re-publication rejection plus asset
hash-dedup (two identical runs publish the same bytes; the first
result set for the key is the one lookups return).

### Effective parameters (§9.3)

- The key is computed from `effective_parameters` when the run
  recorded them (memory recovery), else `requested_parameters` —
  implemented inside `compute_cache_key` (no caller branching).
- "Record the new profile": the adapter already writes
  `effective_parameters` into the run record (M2.5); "show that a
  smaller-segment result was used" is the M2.8 UI's job — the domain
  exposes both parameter sets, and the stored key demonstrably
  matches the effective one (tested).

### Active result selection (§9.4)

> **Design correction (implemented):** the selection lives in
> `PracticeState.active_result_set_id` — the field already added in
> M2.1 (spec §3.5), which stem playback modes already require. An
> early `WorkingState.active_result_set_id` addition was made and
> reverted (net-zero in `domain/project.py`).

- The selection is persisted in the existing `practice_state` column
  (no migration), survives restarts, and is carried by history
  snapshots, so undo/redo restore it.
- New op `SetActiveResultSetOp` (`type = "set_active_result_set"`,
  `result_set_id: Uuid | None` — null clears the selection). It is
  **in** the history (undoable, §9.4.3): not added to
  `HISTORY_EXCLUDED_TYPES`.
- **Clear semantics:** `set_active_result_set(null)` clears the
  selection **and** reverts `playback_mode` to `PlaybackMode.ORIGINAL`
  when in a stem mode (the PracticeState invariant: stem modes require
  an active set). Setting an id keeps the current mode.
- `apply_command` validates the target: the result set must exist for
  the project (query `separation_result_sets` inside the transaction).
  New repository error `ResultSetNotFoundError` → new API error
  (404, code `RESULT_SET_NOT_FOUND`) mapped in
  `command_routes._raise_mapped`. This is the only API-surface change
  (error class + mapping), no new routes.
- **Mechanism (implemented):** `_history_snapshot` takes a
  `practice_state` param (pre-M2.7 snapshots lack the key →
  `_move_history` keeps the current practice state, backward-compat);
  `_apply_op` returns `(markers, working_state, practice_state)`;
  `apply_command` re-validates the full `ProjectRecord` including the
  new practice state; `_write_state` writes the `practice_state`
  column; `CommandResult` gained a `practice_state` field so the
  command endpoint exposes the resulting selection.
- §9.4.1–2 (reruns create new sets; existing sets stay immutable) are
  already true (each completed run publishes its own set; the
  repository has no update path and `publish_result_set` rejects
  re-publication) — covered by regression tests.
- §9.4.4 (never delete a result merely because it becomes inactive)
  is enforced by the retention service below: eviction removes
  rebuildable **bytes** of inactive result sets only under cache-limit
  pressure; the immutable result-set records are never deleted, and a
  set whose assets were reclaimed simply misses lookup (the size
  check) so a rerun rebuilds it.

### Storage policy (§9.5) — `src/basseparate/media/storage_report.py`

- Config: `cache_limit_bytes: int` (new field,
  `DEFAULT_CACHE_LIMIT_BYTES = 50 * 1024**3`, validated ≥ 1 GiB) —
  the 50 GiB configurable cache policy (§9.5.1).
- `StorageReport` (frozen dataclass): `model_bytes`,
  `project_bytes` (source/canonical/derived assets + waveform
  caches), `separation_result_bytes`, `pinned_bytes`,
  `reclaimable_bytes`, `total_bytes`, and the per-result-set
  breakdown (id, created_at, bytes, pinned reason).
- `compute_storage_report(*, paths, model_dirs, repository,
  active_result_set_ids)` (§9.5.2–4, 6):
  - **Model storage counted separately** (`models/` bundle dirs):
    reported, never evicted, never against the limit (§9.5.2).
  - **Pinned**: source/canonical/monitoring assets (M1 policy), stem
    assets of each project's **active** result set (§9.5.3 working
    projects), assets referenced by retained edit history
    (§9.5.4 — M2.7: none yet; the hook takes the referenced-id set so
    M2.8's mixer state can pin its stems), and assets of in-flight
    media jobs (save/export protection, §9.5.6).
  - **Reclaimable**: stem assets of *inactive* result sets
    (everything else is pinned). The newest result set per cache key
    is additionally pinned — it is the entry a lookup would return,
    so evicting it would break "identical separation requests reuse
    results".
- `reclaim_storage(*, report, limit_bytes, asset_dir,
  repository) -> ReclaimResult` — **explicit** cleanup (§9.5.7: the
  report displays reclaimable size *before* cleanup; M2.17 exposes
  both as endpoints): evict reclaimable result sets LRU-first
  (oldest `created_at` first) until `total − model` ≤
  `limit_bytes`, deleting the stem files + their waveform caches and
  leaving the immutable result-set records in place. `ReclaimResult`
  reports bytes freed, result sets evicted, and files removed. Never
  touches pinned bytes; a project's edits (markers, working state,
  history) are project rows, not assets, so they are unaffected —
  the acceptance criterion "edits never disappear because a cache
  entry was reclaimed".

## Out of scope (explicit)

- Scheduler wiring: the M2.17 job pipeline calls
  `lookup_cached_result` → `find_active_run` → `create_run`; the
  "publish only one result" enforcement is the composition of those
  primitives with M2.6's atomic publication.
- API routes for the storage report / explicit cleanup (M2.17) and
  the UI for result-set switching, segment-profile display, and
  reclaimable-size display (M2.8).
- Automatic background eviction: §9.5.7 defines cleanup as explicit,
  after displaying reclaimable size.
- Persisting `PreparedInput` as an asset (deferred from M2.6 to the
  M2.17 decision; the cache key uses its `transform_hash` via the
  reference-mix identity, not a stored prepared-input asset).
